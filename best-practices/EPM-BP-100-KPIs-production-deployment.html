The teaching note (EPM-BP-100-KPIs) said one catalog, many Metric Views, Gold per diverging grain, several Genie agents. This note answers: what does that look like when you are getting ready to run it in production for an enterprise — ~100 certified KPIs from different domains — not a three-KPI Free-edition demo inside one O2C family.

Locks honoured — cite, do not invent
  • C-10: ontology = meaning. Store catalog + consumption semantic layer = certified formula + compute. Ontology does not author formulas. The Store does not author meaning.
  • C-11: never say “semantic layer” unqualified. Say consumption semantic layer or Metric View. Programme compiler seat in demos = Databricks Metric Views / Unity Catalog.

01 What “production” means here

Production, in this note, is not a cloud landing zone and not a headcount of dashboards. It is the moment a finance or ops leader can act on a certified number and trust that every surface they can see agrees.

Certified numbers a leader can act on

A KPI is in production when a named person will take a named action on the published figure — close a period, chase a payer, hold a site, re-cut a plan — and when that figure is the same figure whether they open Gold, run MEASURE(), or ask the Genie agent that is allowed to see that view. If those three can disagree, you are not in production. You are in a demo that has not yet been fenced.

That is RC-1 spoken as an operating rule: one compile path per KPI. The Metric View is the formula object. Gold is a published instance of that compile. Genie is a question set over that compile. None of them is allowed a private SQL copy of the measure.

Environments, not hand-edits

At least two Unity Catalog catalogs: a working catalog and a production catalog. YAML lives in git. A pipeline publishes the Unity Catalog Metric View. Nobody hand-edits a production view, and nobody CREATE OR REPLACEs the whole Store catalog because one KPI moved. Draft work happens in the working catalog. Certification is a status change on a catalog row after the promotion path in §04 is green — not a paste into prod.

The Azure estate is later and out of scope. This note is the Store / consumption shape. It is independent of which cloud landing eventually hosts the catalogs. Do not read an Azure design into these pages.

Working picture — not a lock

Two catalogs (working + production), YAML in git, pipeline publishes the UC Metric View. That is the production-shaped compile path. Exact pipeline product, workspace topology, and catalog names stay open. Do not invent them here.

02 The production estate (scale picture)

Assumed estate: ~100 certified KPIs from different domains. Not 100 measures inside one O2C family. The teaching note’s grouping test still holds; across domains it almost always fails. That is the scale picture this note is written against.

Domains the project has already named: Customer order-to-cash and Ops / Tech plan-to-produce. “Different domains” means those two, plus any other enterprise domain that fails the grouping test — different population, different Silver star, or different grain family. This note does not invent a domain list beyond those names. It does not need one. The test is the partition, not a slide of process names.

03 Four seats in production (what each must have)

C-10 splits meaning from formula + compute. These four seats sit on the formula + compute side. Across ~100 KPIs from different domains, each seat has a production minimum. Fail the minimum and that seat is still a demo leftover.

Catalog — operated register, not a spreadsheet leftover

The catalog is the enterprise register. One row per certified KPI. It can list all 100 because that is its job. It is not the compile and not the meaning SoT. In production it is an operated object: create a row, replace a row by kpi_id, retire a row. Never CREATE OR REPLACE the whole catalog because one KPI moved, one domain onboarded, or one steward changed.

Partition the register by domain (a domain column, and an owner). Customer O2C rows and Ops / Tech plan-to-produce rows live in the same catalog. They do not live in the same Metric View, the same Gold mart, or the same Genie agent. A second competing catalog per domain is not the working picture; mark it open if someone later wants to argue it. Do not stand it from this note.

Status is a lifecycle, not a colour on a slide. Draft means the row exists and the intended measure + view are named; it is not yet a number a leader may act on. Certified means the promotion path in §04 is green and calc_version is frozen. Deprecated means the row remains so old pointers resolve, and so nobody silently republishes under the same kpi_id with a different meaning.

Metric View — the formula object

Git YAML is the authoring source of truth. The Unity Catalog object is the compile. Humans review YAML. A pipeline publishes the view into the working catalog, then into production. The UC object is not hand-edited in prod.

The grouping test is unchanged from the teaching note, and it is stricter once domains differ:

  1. Same population — the same “who counts.” Payer is not sold-to. A site is not a customer account.
  2. Same Silver star — the same fact + dimension family. Different Silver tables get their own view.
  3. Same grain family — the same atomic grain, or a grain that rolls up without rewriting the measure.

Fail any one and the KPI gets its own Metric View. A different domain — Customer O2C versus Ops / Tech plan-to-produce — fails all three in practice. Do not fold them because the catalog already lists both. Inside one domain, a view may still hold a few measures, and only then. Across ~100 KPIs from different domains, expect the view count much closer to 100 than to “a few families.” Exact view-count stays open.

Version 0.1 YAML discipline from the demo still applies: join aliases that do not break the compiler; measures declared so MEASURE() is the only programme path. Only MEASURE() is the programme path (RC-1). A view that compiles but is queried through private SQL is not in production.

No mega-YAML

One file that declares a hundred measures from different domains is not a consumption semantic layer. It is a second catalog pretending to be a compiler. Split YAML the way you split views: by domain, then by the grouping test. Do not invent a file-naming standard in this note.

Gold — published instances

Gold is FROM MEASURE() only. It is a published snapshot of the compile, not a second formula, not formula SoT. Delete-then-insert has a race: a reader can see an empty or partial KPI, or a stale grain beside a new one under the same kpi_id. Prefer one transaction, or a swap of an active-publication pointer. Do not CREATE OR REPLACE an estate-wide table to refresh one KPI.

Share a Gold mart when grain, unit, retention, and access match. One mart per KPI when they diverge. Across different domains that almost always fails. Do not stack O2C instances and plan-to-produce instances in one gold_kpi_value and hope a kpi_id column sorts it out. The demo folded three related O2C KPIs into one table. That taught the compile path. It is not the production shape of a cross-domain estate.

Carry calc_version, the as-of, a source / population pointer, and published_at on every published row. Production readers hit Gold or MEASURE(). They never hit a private SQL copy, a notebook leftover, or a Power BI measure that re-implements the formula. Drift check: Gold versus live MEASURE() on the same grain, same calc_version, and same as-of. If they do not match, Gold is not published. It is a rumour.

Gold physical form at programme scale stays open. Share a mart when grain, unit, retention, and access match; one mart per KPI when they diverge. This paragraph is not a lock on storage layout, clustering, or table names.

Genie — a question set, not the enterprise

One agent = one charter: which job, which views, which grains. Customer O2C is one charter. Ops / Tech plan-to-produce is another. A hundred KPIs from different domains do not share an agent. Exact agent-count is open; the floor is one agent per consumption context / domain job.

Instruction text and example SQL live in the same repo as the views. There is one write path into the Genie Text box — the script string is the instruction. Do not keep a parallel “real” instruction in a slide, a wiki, or a chat. The confuse-set is a release gate, not a chat hobby. It runs in a fresh conversation after every instruction or view change that agent can see.

No Export-to-metric-view. No second formula. The Genie fence is attached objects intersect the asker's Unity Catalog grants intersect the Genie service grants. Attachments are not a wall. Never attach fct_* or raw_*. Revoke leader SELECT on those objects. Cross-domain numbers do not go into a mega-Genie. They go to the catalog (which KPI, which view, which Gold) or to a composed report that already joined certified Gold / MEASURE() results.

04 Promotion path for one KPI (the unit of production)

A KPI is not “in production” until all of the following are true. This is a short sequence, not a workshop, not a gate register, and not an artifact ID. The unit is one KPI. The estate is ~100 of these, from different domains, each walking the same path onto its own domain’s seats.

1

Meaning exists. An ontology class / term, with includes and excludes. The Store does not invent the term (C-10). If the class is missing, stop. There is nothing to certify.

2

Catalog row in draft. Points at the intended published measure and the intended Metric View. Domain / owner set. Status = draft. The row is a reservation, not a certified number.

3

Metric View YAML in git, reviewed, published to the working catalog. MEASURE() fixture passes — enterprise total and each certified grain. Join aliases that the compiler accepts. Only MEASURE() is the path.

4

Gold mart published FROM that MEASURE(). Delete-then-insert has a race (empty or partial KPI, or a stale grain beside a new one). Prefer one transaction, or a swap of an active-publication pointer. Carry calc_version, as-of, a source / population pointer, and published_at. Drift check against live MEASURE() on the same grain, same calc_version, same as-of is green. Share the mart when grain, unit, retention, and access match. Not an estate-wide gold_kpi_value.

5

Attached to the right existing Genie agent — that domain’s agent, that job’s charter. Or a new agent if the question set is a new job (the KPI is the first of a new consumption context). Instruction and example SQL updated in the same change, same repo, one write path into the Text box. Do not bolt an Ops / Tech KPI onto the O2C agent. Do not bolt a new domain onto an agent that already has a different population.

6

Confuse-set run in a fresh conversation. Pass = the agent picks the right view, equality holds on the named grain, no ILIKE OR, no extra GROUP BY. Fail = the KPI is not certified, whatever the fixture said.

7

Catalog status → certified. calc_version frozen until the next formula change. Production readers may now act on the number. The working-catalog objects are promoted by the pipeline; they are not hand-copied.

A formula change is a new calc_version

Not a silent overwrite. YAML changes in git. The view republishes. Gold is republished FROM the new MEASURE(). Drift is re-checked. The confuse-set runs again in a new chat — old threads are discarded; they replay the old instruction. The catalog row keeps the same kpi_id and advances calc_version. Deprecated is for meaning or identity retirement, not for a formula bump.

05 Access, identity, and what Genie must not see

The fence is what makes a hundred cross-domain KPIs survivable. Genie will guess. Design assumes it will. The identity that serves production questions is not allowed to see the tables a guess would be interesting on.

Never attach fct_* or raw_* to Genie. That is necessary and not enough. Databricks will query past the attach list if the asker has SELECT. The real fence is attached objects intersect the asker's Unity Catalog grants intersect the Genie service grants. Attachments are not a wall. Revoke leader SELECT on raw_* and fct_*. Leaders must not have SELECT on Lakebase ODS or bronze. Attaching the fact “just in case” is how an O2C agent starts answering plan-to-produce questions with an ILIKE.

Humans who author YAML are not the same role as humans who ask Genie. Authors need the working catalog, the repo, and the pipeline. Askers need the production agent for their job. Crossing those roles in one identity is how a “quick fix” becomes a second formula.

“Customer” is not a grain. Party roles stay payer / sold-to / site / product. A Genie that is allowed to group by a polite word instead of a role will invent a population the Metric View never certified. That failure is worse across domains, because the polite word is shared and the populations are not.

06 Operability

Production is a loop, not a launch. The same four seats that hold the estate are the four seats you watch. Nothing below invents a workshop or a gate ID. It is the minimum you run so a certified number stays the certified number.

What you watch, and what a fail means
WatchGreen looks likeFail means
Compile health The view still compiles. MEASURE() fixtures still match expected totals, or a documented as-of change explains the delta. The KPI is not certified today, whatever the catalog status still says. Do not let Genie keep answering from a broken compile.
Drift Gold snapshot equals live MEASURE() on the same grain, same calc_version, same as-of. Readers must not use Gold until it is republished FROM the compile. A dashboard on drifted Gold is a second number.
Genie Confuse-set run after every instruction or view change that agent can see. Fresh conversation. Right view, equality, no ILIKE OR, no extra GROUP BY. The agent is not a production surface until it passes. The catalog and Gold can still be.
Lineage Readable from catalog row → Metric View → Silver star → ontology IRI. A number with no pointer is not a certified KPI. Fix the row; do not write a paragraph in Genie to paper over it.
As-of / late facts The as-of rule lives on the catalog row and in the view. Fixtures know the rule. An as-of that exists only in a Genie paragraph will drift the first time a late fact arrives. That is a second formula in prose.

As-of and late-arriving facts are an operability concern, not a Genie concern. The rule is declared once, on the catalog row and in the view. Genie may be told the rule so it does not invent a different one. It may not be the only place the rule lives.

07 Edge cases stay the same, but they are a release gate

The teaching note already named the edges. In production they do not become a research backlog. They become the reason a KPI stays in draft. Across different domains the same edges are more expensive, because a guess that escapes the fence can land in the wrong process.

  • New confuse-case = new example SQL + one Don’t line. Same change, same repo, same write path into the Text box. Do not write a second architecture to contain one bad answer.
  • One write path. The Genie Text box is the script string. Instruction and example SQL are files next to the views. There is no parallel “real” copy.
  • New chat after any edit. Old threads replay old instructions. A formula change, an instruction change, or a view republish all discard the old conversation.
  • Cannot fully stop GROUP BY ALL / ILIKE / thread replay. Production design assumes they happen. The fence — small view set on that agent, no raw tables, no other domain’s views — is what contains them. A hundred cross-domain KPIs on one agent is how you take the fence down.
  • Optional later: a knowledge store of exact party names. Not required to call the shape production. Do not claim Databricks will stop ILIKE. Do not wait for that claim before fencing identities.
The fence is the containment

You will not talk the model out of guessing. You will not get a platform promise that ILIKE is gone. You attach one job’s views, you deny bronze, and you re-run the confuse-set. That is the production answer to the same edges the demo already showed.

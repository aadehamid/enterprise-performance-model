## Context

The ontology is done (EPM-DEC-001-0107), and the pricing demo rebuilds the pricing assets in Databricks Free Edition with synthetic data (EPM-DEC-001-0102). Since 2026-10-28 its source databases run on an exe.dev VM (EPM-DEC-001-0102, amendment of 2026-10-28). Part 2 of the work connects the two: Databricks agents that answer from the ontology. Claude put the design to the decision owner as a grill, in four rounds of questions with a recommendation each.

What Claude found first, from the repository:

- Only one measure had an identifier: Crack Spreads Pricing carries KPI-0001, the crack-spread Genie agent's identifier (EPM-DEC-001-0097, item 3). The `kpi` module holds 41 measures in eight kinds, and classes Crack Spreads as a market indicator.
- The demo has two Genie agents: Crack Spread Price Analytics, bound to the crack-spread metric view, and Executive Summary KPIs Analytics, bound to the Executive Summary and benchmark-prices metric views. A refinery operations metric view already holds utilization, planned utilization, yields, R&M margin per barrel, margin capture and opex per barrel over 1,846 refinery-days. *2026-10-28, later:* 9,724 refinery-days since the three-year extension (`demos/downstream-pricing-databricks-free/DATA.md`). *2026-10-29:* four Genie agents since PR E4 (decision 3 below).
- The projection driver writes the whole ontology to Databricks as a Delta table of triples, `epm_triples`.

What Claude found from primary sources, on 2026-10-28:

- Databricks has a Supervisor Agent in Agent Bricks, generally available, which routes a question to Genie agents and other subagents, and the SDK creates it (`w.supervisor_agents`) (docs.databricks.com, "Use Supervisor Agent to create a coordinated multi-agent system"; the Databricks blog, "Agent Bricks Supervisor Agent is Now GA"). *2026-10-29:* the same page, updated 2026-10-14, now marks Supervisor Agent legacy and "not recommended for new systems", and its SDK management Beta; this account can no longer create one (decision 3's note).
- Databricks Free Edition's limits page (updated 2026-10-18) lists no Supervisor Agent limit, and says "outbound internet access is restricted to a limited set of trusted domains" (docs.databricks.com, "Databricks Free Edition limitations").
- Composite databases are "Enterprise Edition" and "Not available on Aura" (Neo4j Operations Manual, "Composite databases: Concepts").

**What follows (Claude, under EPM-DEC-001-0028):**

1. **Identifiers,** in `kpi` 1.3.0. KPI-0001 stays Crack Spreads Pricing, because the pricing assets use it, although the module classes it as a market indicator. The two measures classed as KPIs take KPI-0002 and KPI-0003. Every operational metric, market indicator, plan-variance diagnostic, decision-support indicator and alert takes an OPM identifier, OPM-0001 onward, in the module's order: 30 measures. In round 2 Claude told the decision owner 31, counting Crack Spreads among the market indicators; the rule, not the number, is what was decided, and Crack Spreads keeps KPI-0001. Trackers, reports and non-measures take none. Four digits keep the identifiers sorting as text and give one pattern per prefix. A measure promoted to KPI later takes a new KPI identifier; its OPM identifier is kept and never reused.
2. **Metric views** are grouped by fact grain: one view per subject area that shares a fact and its dimensions, never one per measure. A new view, `pricing_market_margin_metrics_vw`, holds the six market-price measures (Gasoline, Distillate and Crude Market Pricing, Price Comparison, Additional Market Prices and the R&M Margin Indicator). R&M Margin per Barrel and Margin Capture stay in the refinery operations view, at refinery-day grain. Each measure carries its identifier in its name and comment, and each view a tag listing the identifiers it implements. Where the price catalog has no renewables or NGL series, the demo adds synthetic ones, labelled so. *2026-10-29:* landed in PR E3, with these build choices, delegated under EPM-DEC-001-0028: each measure that implements a `kpi` measure carries its identifier in its comment, its display name and its synonyms, not in its name, because the Genie agents and the shared pricing assets query the measures by name (EPM-DEC-001-0097); each view's comment and a Unity Catalog tag, `epm_measure_identifiers`, list its identifiers. The R&M Margin Indicator is not computed, because `kpi` gives its basis as not published; the pricing view's comment says so. The price catalog already held renewables and NGL series, so none was added. Unit Utilization (OPM-0001) has its own view, `refinery_unit_operations_metrics_vw`, at unit-day grain.
3. **Genie agents:** one per subject area. Crack Spread Price Analytics and Executive Summary KPIs Analytics stay, and a Pricing and Market Margin agent joins them, with a Refinery Operations agent over `refinery_operations_metrics_vw`, the refinery-day subject area the use cases below need. A Supervisor Agent routes between the four, and each subagent's description names the identifiers it answers for, built from `epm_triples`. If Free Edition refuses the Supervisor Agent, the fallback is Databricks' documented multi-agent app pattern, and the record of the run says which ran. *2026-10-29:* landed in PR E4, with these build choices, delegated under EPM-DEC-001-0028. The Refinery Operations agent also binds `refinery_unit_operations_metrics_vw`, the unit-day view E3 added for Unit Utilization. Free Edition refused the Supervisor Agent: `create_supervisor_agent` returned "PermissionDenied: Supervisor Agent is now a legacy feature. New instances can no longer be created for this account. Please use Genie Agents instead." Databricks' page marks it legacy too ("Use Supervisor Agent to create a coordinated multi-agent system (legacy)", updated 2026-10-14). The fallback ran: the documented pattern ("Build a multi-agent system on Databricks Apps", updated 2026-10-14), in which an orchestrator model treats each subagent as a tool chosen by its description. The demo runs it from the laptop (`python -m pricing_demo.supervisor ask`), not deployed as a Databricks App; its model is `databricks-meta-llama-3-3-70b-instruct`, which the function-calling page lists ("Function calling on Databricks", updated 2026-10-26), because this workspace does not serve the template's `databricks-claude-sonnet-4-5`; and it calls each Genie agent through the Genie Conversation API ("Use the Genie Agents API", updated 2026-10-23), not the Genie MCP server the template uses. Each subagent's description is built at run time from its definitions view (identifiers and labels from `epm_triples`) and its metric views' `epm_measure_identifiers` tags; an identifier the definitions view holds but no tag lists, OPM-0026, is marked "defined, not computed". The multi-agent page is itself marked legacy and points new work to the Agent Bricks CLI.
4. **What the agents read:** the Turtle in git is the source of truth; `epm_triples`, AuraDB and the local Neo4j are projections kept in sync with it. Inside Databricks the agents read the ontology from `epm_triples`, through a definitions view per agent. *2026-10-29:* the definitions views landed in PR E3, in their own schema, `ontology_definitions` (delegated under EPM-DEC-001-0028): `measure_definitions_vw`, every measure with an identifier, and one view per subject area (crack spread, Executive Summary, pricing and market margin, refinery operations). No agent reads them yet. *2026-10-29, later:* since PR E4 each of the four Genie agents binds its subject area's definitions view, and its instructions tell it to read each measure's definition, grain, basis and not-to-be-confused-with labels there before answering.
5. **Lineage:** each place answers for its own scope. The ontology holds designed lineage (the `data-product` module's pricing tables and their lineage by layer); Unity Catalog records observed lineage in its system tables; Neo4j's technical graph holds what runs outside Databricks. A test compares designed and observed lineage after each demo run and names any edge found in only one. If Free Edition lacks the lineage system tables, the test is skipped with that reason. *2026-10-29:* landed in PR E5 (delegated under EPM-DEC-001-0028). Free Edition has the lineage system tables, so the test ran: it reads the `data-product` module's table lineage (`prov:wasDerivedFrom` between its tables) from `epm_triples` and Unity Catalog's `system.access.table_lineage`, keeping each table's edges from its latest build. 26 edges matched, 5 were designed only (the demo's silver price master and crack-spread gold read fewer tables than the shared asset's), none was observed only, and 9 designed edges touch MPR reference tables the demo does not build. The test is one of the technical graph's data-quality checks (decision 6).
6. **The technical graph:** about 100 nodes describing the demo pipeline, which the business ontology does not model: the six source databases on the exe.dev VM (*2026-10-28, later:* seven, with `eia_weekly`), the replication and build steps, every table and view at each layer with its row count and last refresh, and the data-quality checks with their last result. Each node links to the ontology by IRI where one exists (system, data product, KPI or OPM identifier). It lives in the local Neo4j and in AuraDB under a `Tech` label, in the same database as the ontology, so one Cypher query walks from a gold table to the measure it implements. The projection's counts and hashes count only the ontology's labels. *2026-10-29:* landed in PR E5, built from the demo's files with SPARQL Anything 1.3.0 (delegated under EPM-DEC-001-0028). 102 nodes: the 63 tables and views, 8 source databases and their host, the 17 steps of the README's run commands, 7 data-quality checks with their last result, the 4 Genie agents, the orchestrator and `epm_triples`. Its links to the ontology go to `kpi` measures (through each metric view's identifier tag), `data-product` tables and agents, and `system` systems. The decision trail joins it as PROV-O: 10 decisions and 22 evidence items from the two tables the agents see, linked to `organization` roles, `ref-mpc` refineries and `kpi` measures. In both local Neo4j stores and AuraDB its 134 nodes carry the label `Tech` and no `Resource` label, and every edge starts at a `Tech` node; the projection's counts and hash read only `:Resource` nodes and the edges between them, so they did not change when it loaded, and `projection/test_pipeline.py` pins that its queries read nothing else. A pipeline reload or a driver run empties its store, so the demo's `tech_graph load` runs again after one.
7. **Databricks and Neo4j:** a sync step run from the laptop copies the technical graph into two Delta tables, `tech_graph_nodes` and `tech_graph_edges`, which the agents read; Neo4j stays the source. A live connection from Databricks to AuraDB is tried and reported, with the AuraDB login in a Databricks secret scope written from the local login file without printing it. Free Edition's restriction on outbound access may block it; the record of the run quotes the error if so. *2026-10-29:* landed in PR E5 (delegated under EPM-DEC-001-0028). `tech_graph sync` copied the graph from the pipeline's Neo4j into `idp_sbx.tech_graph.tech_graph_nodes` (134 rows) and `tech_graph_edges` (510 rows); no Genie agent binds them yet. The AuraDB test was not blocked: a one-time serverless job read the login from the secret scope `epm-neo4j`, written without printing it, resolved AuraDB's host, opened port 7687 and ran a Bolt query that counted 4,193 ontology nodes.
8. **The data extension:** three years of refinery operations with process units (about 14,000 refinery-days and about 140,000 unit-days), monthly plan targets for the same span, and three years of EIA price history fetched with the current EIA key. `rightangle` and `reference_data_hub` stay as they are. A data description document gives every table, its grain, its row count, how it is generated and a link to the script that generates it. *2026-10-28, later:* built over 748 trading days (2023-10-21 to 2026-10-20), because each refinery-day joins that day's crack: 9,724 refinery-days and 76,296 unit-days, fewer than the estimate above, and 481 monthly plan targets (13 refineries over the 37 calendar months the window touches). Freight landed in `rightangle` and the event table in `reference_data_hub`, so those two databases did change; EIA's weekly data by PADD landed in a seventh database, `eia_weekly`. `demos/downstream-pricing-databricks-free/DATA.md` is the data description document.

## Alternatives considered

- **IDs for all 41 measures as KPIs.** Claude's round 1 recommendation; not chosen. The decision owner separated KPIs from operational metrics.
- **Renumbering Crack Spreads as an OPM.** Not chosen: it would break the pricing assets' KPI-0001.
- **No padding.** Not chosen: identifiers would sort wrongly as text (KPI-10 before KPI-2).
- **One metric view or one Genie agent per measure.** Not chosen: it repeats joins and dimensions and gives Genie more places to choose between.
- **A composite database for the ontology and the technical graph.** Not chosen: composite databases need Neo4j Enterprise Edition, which this machine does not have, and Aura does not offer them.
- **AuraDB as the agents' source inside Databricks.** Not chosen: Genie queries only Unity Catalog tables, and Free Edition restricts outbound access.

## Question 2: change the merge rules so a medium-risk PR waits for you?

What the repo holds. Nothing in the repo controls Cursor's merges. `.cursor/` holds only `environment.json` and `install.sh`, and `.github/workflows/` holds `checks.yml` and `links.yml`. `main` has no branch protection (`gh api .../branches/main/protection` returns "Branch not protected") and no rulesets (`gh api .../rulesets` returns `[]`). The automation's own instructions are in the Cursor dashboard at https://cursor.com/automations/8ee34ca9-c063-11f1-bb68-864e54d14197. I could not read them.

What the approval agent already does. It leaves a GitHub APPROVED review on PRs it rates eligible. It did so on 17 of PRs #240 to #270 (for example #261, #264, #267, #268 and #270), and it did not on #262, #266 or #269 (`gh api .../pulls/<n>/reviews`).

### Options

- (A) Add a GitHub ruleset on `main` that requires the `checks` status check to pass and requires one approving review. Add yourself to the ruleset's bypass list. (Recommended) Reason: GitHub enforces it, so it does not depend on how the bot reads the policy, and the bot has already overruled the approval agent three times. GitHub's rules say "all required status checks must pass before collaborators can merge" and, with required reviews, a change needs approval "by the required number of reviewers with write permissions" (https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets, read 2026-10-14). If you choose this, low-risk PRs still merge after the approval agent approves them, and a medium-risk PR stays open until you review it and merge it through the bypass. No PR can merge before CI finishes. Test it on the next low-risk PR. I have not confirmed that an approval from `cursor[bot]` counts as a required approval. If it does not, every PR would wait for you until the rule is adjusted.
- (B) Edit the review automation's instructions in the Cursor dashboard so it does not merge when the approval agent has not approved, or when `checks` has not finished. Reason: it is a small change with no GitHub setup. It still depends on the bot following its prompt. If you choose this, the repo does not change, and the rule has no record in the repo unless I add a line to `APPROVAL_POLICY.md` in a PR.

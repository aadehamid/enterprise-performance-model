The EPM ontology

A guide to the ontology of Marathon Petroleum's downstream business: what it is for, why it is split into eleven modules, what each module holds and how the modules connect. One pricing measure, the crack spread, runs through every section to show the modules working together.

What it is for

The ontology is one shared, checked vocabulary for how the downstream business works. It names the processes and how they relate, the roles that do them, what each measure means, which market series and data products carry the numbers, and which systems hold the data. A person, a report or an AI agent can then ask one question across all of it, such as "what does the crack spread mean, which view gives its value, and who works on the processes it informs?", and get an answer that cites its sources.

It holds definitions, never records. Actual customers, invoices and measure values stay in the business systems. The playbook's policy 2 calls this "define, don't record" (MODULES.md, "Three kinds of content").

Three kinds of content, each in a fixed place

DefinitionsClasses, properties, role types. In organization, party and the other modules.
Company-neutral instancesThe role register, RACI assignments, customer lifecycle stages, the process map itself.
Company-specific instancesMPC, MPLX, MPC's control of MPLX, the 13 refineries. In ref-mpc only.

Source: MODULES.md, "Three kinds of content"; EPM-DEC-001-0015.

The W3C standards it is built on

RDFEvery fact is a triple: subject, property, object. Each module ships as Turtle and JSON-LD.
SKOSTaxonomies and code lists: the process hierarchy (skos:broader), measure kinds, office lanes, and the labels and definitions on every concept.
OWLThe classes and properties each module defines, such as kpi:MeasureDefinition and dp:servesMeasure.
SHACLShapes in every release (shapes.ttl) that say what valid data looks like. All modules' shapes run together over the whole graph, with zero violations (EPM-DEC-001-0065).
W3C ORGRoles (org:Role), sites and organizations, in organization and ref-mpc.
PROV-OLineage: a metric view prov:wasDerivedFrom its gold table, and a Genie agent prov:used the view.
DCATThe catalog of every released package, releases/catalog.ttl.

Why modules

The ontology could have been one large file. It is eleven modules because each part has its own owner, its own sources and its own pace of change.

The ontology skill's playbook, "Why split an ontology into modules", gives the reasons, and the build followed each one:

  1. Each module releases on its own schedule. When item F changed the pricing measures, kpi went to 1.2.0 and core stayed at 2.3.0. Each module pins the versions it requires.
  2. Reviews and approvals stay small. A pull request touches one module, and its owner approves it.
  3. Company facts sit apart from neutral ones. MPC's refineries and MPLX live in ref-mpc, so every other module could serve another refiner (EPM-DEC-001-0015).
  4. Each module carries its own shapes and tests, and a whole-graph gate catches what breaks between them (EPM-DEC-001-0065).
  5. Consumers load only what they need. A package's dependencies are read from the released manifests.
  6. A projection can tag every node with its module, so a walk across the graph shows where each fact came from.

Two rules keep the split sound. The module policy (the skill's foundations.md, policy 8) says modules depend one way, with no cycles, and use each other's terms by IRI, never by redefining them. A cycle would make a module impossible to release on its own.

Some splits follow the business's own lines. Market Data is a domain separate from commercial pricing, so its benchmark recipes have their own module (EPM-DEC-001-0006). The cross-module rules (what certifies, which source wins, what an agent may answer) sit in one integration package above the rest.

The split has a cost. A module's pin can lag: organization 2.0.0 was released against core 2.1.0, and lane 1.0.0 against core 2.2.0, though core is now 2.3.0. That is why the closure rule, the whole-graph gate and each changelog's list of required versions exist.

The module map

core, the process map, is at the bottom. Most modules add one kind of thing and link it to core's processes. An arrow points from a module to a module it requires, as each release's manifest records. integration requires all the others.

One measure, every module

Take one measure, Crack Spreads Pricing (measure:crack-spreads, identifier KPI-0001), and follow its links. Each module adds one piece of context, and together they answer what the number means, where it comes from, who works with it and what may be said about it.

The walk, as one query

This SPARQL query walks the measure's neighbourhood across eight modules. It runs over the eleven newest releases loaded together; the output below is what it returned on 2026-10-26.

PREFIX skos: <http://www.w3.org/2004/02/skos/core#>
PREFIX dcterms: <http://purl.org/dc/terms/>
PREFIX kpi: <https://w3id.org/lsc/ontology/modules/kpi/>
PREFIX mkt: <https://w3id.org/lsc/ontology/modules/market-data/>
PREFIX dp: <https://w3id.org/lsc/ontology/modules/data-product/>
PREFIX sys: <https://w3id.org/lsc/ontology/modules/system/>
PREFIX vs: <https://w3id.org/lsc/ontology/modules/value-stream/>
PREFIX orgm: <https://w3id.org/lsc/ontology/modules/organization/>
PREFIX measure: <https://w3id.org/lsc/ontology/modules/kpi/measure/>
SELECT ?hop ?label WHERE {
  { measure:crack-spreads kpi:measureKind/skos:prefLabel ?label . BIND("kind (kpi)" AS ?hop) }
  UNION { measure:crack-spreads kpi:informsProcess ?p . ?p skos:notation ?n ; skos:prefLabel ?l .
          BIND("informs process (core)" AS ?hop) BIND(CONCAT(?n, " ", ?l) AS ?label) }
  UNION { ?s mkt:seriesOf measure:crack-spreads ; mkt:region/skos:prefLabel ?r ; skos:prefLabel ?l .
          FILTER(?s = <https://w3id.org/lsc/ontology/modules/market-data/series/crack-gulf-coast-3-2-1>)
          BIND("series (market-data)" AS ?hop) BIND(CONCAT(?l, ", ", ?r) AS ?label) }
  UNION { ?v dp:servesMeasure measure:crack-spreads ; skos:prefLabel ?label .
          BIND("served by view (data-product)" AS ?hop) }
  UNION { ?v dp:servesMeasure measure:crack-spreads ; dp:dependsOnSystem/skos:prefLabel ?label .
          BIND("view reads system (system)" AS ?hop) }
  UNION { ?v dp:servesMeasure measure:crack-spreads ; dcterms:isPartOf/skos:prefLabel ?label .
          BIND("part of data product (data-product)" AS ?hop) }
  UNION { ?step vs:measureLink [ vs:measure measure:crack-spreads ; vs:relationship/skos:prefLabel ?rel ] ;
                skos:prefLabel ?l .
          ?stage vs:hasProcess ?step . ?stream vs:hasStage ?stage . ?stream skos:prefLabel ?sl .
          BIND("value-stream step (value-stream)" AS ?hop) BIND(CONCAT(?l, " [", ?rel, "] in ", ?sl) AS ?label) }
  UNION { ?v dp:servesMeasure measure:crack-spreads ; dp:dependsOnSystem ?sy . ?sy sys:supports ?p .
          ?p skos:notation "CM 1.1.5.1.2.6" ; skos:prefLabel ?pl .
          ?a orgm:forProcess ?p ; orgm:assignedRole/skos:prefLabel ?role ; orgm:raciLevel/skos:prefLabel ?lvl .
          BIND("RACI on a process MPR supports (organization)" AS ?hop) BIND(CONCAT(?pl, ": ", ?lvl, " ", ?role) AS ?label) }
}

Each module

Each module below says what it holds, why it exists, what it links to, and its part in the crack spread's story. The counts are from its newest release.

core 2.3.0 19,819 triples

Holds the process map: 463 processes, 23 capabilities and 2 structural anchors as a SKOS hierarchy under Downstream Operations and Enabling Functions. Each process has a notation (CM 1.1.4.7.4), a definition, a parent, and fields such as cadence, operating mode and business domain. It also holds 640 approved relationships between processes, such as core:informedBy and core:precedes, each as a direct triple and as a canonical-fact node that carries its evidence row.

Why: the process map is the authority every other module hangs on. It is built from business_architecture/business_process/downstream_process_map.json, and changes to the map go through proposals, never direct edits (AGENTS.md).

In the crack spread's story

The measure informs proc:CM-1-1-4-7-4, Capture Product/Crude/Feedstock Price, a monthly step of Refinery Optimization (CM 1.1.4.7), under Refining. Its definition: "Establish the price and economic assumption set used to value crude, feedstock, and finished-product streams in the optimization case". Six other price measures inform the same process.

Links: the other modules point at core's process IRIs (https://w3id.org/lsc/ontology/process/CM-…); core itself requires nothing. Open: 462 relationship mentions held for review, and the seven preferred labels shared inside the process scheme (EPM-DEC-001-0098, item 8).

kpi 1.2.0 1,157 triples

Holds 41 measure definitions, each classified by its kind: 15 operational metrics, 7 market indicators, 6 trackers or reports, 6 plan-variance diagnostics, 2 KPIs, 2 alerts, 1 decision-support indicator and 2 "not a measure". It also holds the four planning personas who use them. Eight measures carry their population, what they include and exclude, in MPC's own wording.

Why: one meaning per measure, kept apart from any value, so that every report and agent uses the same definition (EPM-DEC-001-0040, 0042, 0043). It is seeded from the planning team's measure list; filings are evidence for a definition, not a source of values (EPM-DEC-001-0017).

In the crack spread's story

The definition lives here: measure:crack-spreads, "Crack Spreads Pricing", identifier KPI-0001, kind market indicator, grain "daily, by market hub", compared against a 30-day trend and 5-year history. It names three measures it is not to be confused with, such as margin capture. Its population excludes "the market cost of RINs, in MPC's 10-K regional and blended crack spreads".

Links: kpi:informsProcess to core. Requires core 2.3.0. Open: who owns each measure's meaning (competency question 17, business close-out point 1), and the populations of the other 33 measures (point 10).

market-data 1.1.0 1,403 triples

Holds the recipes of market series, never their prices: 15 benchmark series, their 28 legs over 24 benchmarks, refining and market regions, and 40 named market prices (mkt:MarketPrice) that the pricing measures present. Its shapes reject a price value.

Why: Market Data is a domain of its own, separate from commercial pricing, and owns benchmarks and their methodology (EPM-DEC-001-0006). For the crack spread, MPC Economics' definition is the primary source, then MPC's filings, then peers, then exchanges (EPM-DEC-001-0066).

In the crack spread's story

Fifteen series name the measure through mkt:seriesOf. The Gulf Coast 3-2-1 is three barrels of MEH crude producing two of USGC CBOB gasoline and one of USGC ULSD, in the Gulf Coast region. The region is MPC's Galveston Bay and Garyville refineries. A series enumeration records 127 series in 44 groups in the crack-spread view on 2026-10-25.

Links: mkt:seriesOf to kpi's measures. Requires kpi 1.2.0. Open: Market Data accountability. The Risk Group holds it provisionally, until its mandate is confirmed (EPM-DEC-001-0046; close-out point 2).

data-product 1.2.0 1,442 triples

Holds the data-product portfolio: segments, 19 product lines and 49 data products (16 defined so far). Since 1.2.0 it also holds the pricing platform's 33 tables and views, by layer: replica, silver, gold and metric view. Each carries its kind, foundational or derived, its lineage (prov:wasDerivedFrom), its systems and the measures a view serves.

Why: a measure means something only if a consumer can find the data that gives its value. This module connects the business's data products to the platform objects that implement them (EPM-DEC-001-0053, 0100).

In the crack spread's story

The metric view mpr_mips_crack_spread_price_fact_metrics_vw dp:servesMeasure the crack spread. It is a derived data product in the metric-view layer and part of Master Pricing, in the Market Structure & Logistics Management line. It derives from the gold crack-spread fact, whose Crack_Spread_Price_Amount column derives from MPR's settle price. The Crack Spread Price Analytics Genie agent uses it.

Links: dp:servesMeasure to kpi, dp:dependsOnSystem and dp:copiesSystem to system, dp:producedBy and dp:consumedBy to core. Requires core 2.3.0, kpi 1.2.0 and system 1.2.0. Open: 33 data products have no definition yet.

system 1.3.0 793 triples

Holds 34 systems, office tools and working documents: the 32 the process map names, plus MIPS and Databricks. 32 have a definition. Each says which processes it supports, taken from the process map's "systems" fields (EPM-DEC-001-0055, 0099, 0103).

Why: to answer which tool a process runs on, and which system a data product reads. Names were merged on spelling, so one system has one IRI.

In the crack spread's story

The crack-spread view depends on MPR, MIPS and KittyHawk. MPR is the price master. It holds each priced instrument and its daily price details and settlement prices, and supports eight processes, such as CM 1.1.5.1.2.6 Receive actual data product prices. MIPS holds market price assessments in sheets, groups and batches.

Links: sys:supports to core. Requires core 2.3.0. Open: TopDay and VALT wait for their owners' descriptions (close-out point 12); CargoTracker, Allocation Manager, Hyperion, Quorum and Polaris need fuller answers (points 13 to 15).

organization 2.0.0 5,987 triples

Holds 60 roles (positions, never people) and 940 RACI assignments, each a node of its own that names its process, role and level. It also defines the control relationship between legal entities (EPM-DEC-001-0030, 0045).

Why: to say who does what on each process, by role. A RACI assignment is a node, so it can carry its own level and source, as the playbook's qualified-relation pattern requires.

In the crack spread's story

On Receive actual data product prices, which MPR supports, the Continual Commercial Improvement Director is accountable, a Business Analyst responsible, and a Pricing Representative consulted. That is the team that receives the prices the crack spread is built from.

Links: orgm:forProcess to core. Requires core 2.1.0, a pin that lags core's 2.3.0. Open: the Forecaster, Crude RFC and PSM readings and four working definitions (close-out points 6 to 9).

value-stream 1.1.0 995 triples

Holds two value streams, Commercial Hydrocarbon Lifecycle and Order to Cash, with 12 stages, 58 steps and 21 capabilities. A step vs:realizes core processes, vs:produces and vs:consumes data products, and links to the measures it moves through a measure link that names the relationship (EPM-DEC-001-0054).

Why: the process map says what the business does. The value streams say how value flows end to end, as an overlay that references the map and never changes it.

In the crack spread's story

Market Price Calculation & Validation, in the Market & Strategy Formation stage, uses the crack spread as a benchmark. It "transform[s] raw market data and internal price assessment into official, validated system of record for all product prices". It produces Master Pricing, the data product its view belongs to, and realizes three pricing processes, such as CM 1.3.6.3 Sales Pricing Management.

Links: vs:realizes to core; vs:produces and vs:consumes to data-product; vs:measure to kpi. Requires core 2.3.0, data-product 1.0.0 and kpi 1.1.0.

party 1.3.0 4,020 triples

Holds the customer domain: the customer model with 20 concept schemes, 42 customer systems with 35 data flows and 275 attributes, 27 products, and the customer lifecycle in a business view and a system view (EPM-DEC-001-0068 to 0070).

Why: the customer domain has its own owner and its own sources, the customer systems' data flows, and changes on its own schedule.

In the crack spread's story

KittyHawk, one of the view's three systems, is also a customer system. party:system/kittyhawk skos:exactMatch system:kittyhawk says they are the same system. The customer view adds that it "records physical product movements" and receives customers from RightAngle.

Links: party:stageProcess to core, skos:exactMatch to system. Requires core 2.3.0 and system 1.3.0. Open: four customer systems and four codes wait for their owners (close-out points 3, 4 and 11), and the product list awaits confirmation (point 5).

ref-mpc 1.2.0 180 triples

Holds the company facts: MPC and MPLX, MPC's control of MPLX, its three reportable segments and its 13 refineries, each dated to 31 December 2025 from MPC's FY2025 Form 10-K. It defines no terms of its own; it uses those of organization and party.

Why: it is the only company-specific module, so every other module stays company-neutral and reusable (EPM-DEC-001-0015, 0033).

In the crack spread's story

The measure's public counterpart is MPC's own Gulf Coast, Mid-Continent, West Coast and blended 3-2-1 cracks. Its value-stream link cites MPC's FY2025 10-K, Item 7. The Garyville refinery here sits "in MPC's Gulf Coast refining region", the region of the Gulf Coast series. That tie is a note today, not a triple.

Links: uses organization's and party's classes and properties. Requires organization 2.0.0 and party 1.0.0.

lane 1.0.0 59 triples

Holds the four office lanes, Front Office, Middle Office, Operations and Back Office, and the seven processes the process map places in them. Each is a child of Supply And Trading (CM 1.2), such as Trading Management in the front office and Settlements & Accounting in the back office. A child does not inherit its parent's lane (EPM-DEC-001-0056).

Why: a trading organization divides its work by lane, and the map states the lane for these processes only.

In the crack spread's story

The crack spread does not touch a lane. Its processes sit in refinery planning (under Refining), regional backcasting and marketing, and the map places none of them in an office lane. That is an honest gap, not an error: the ontology states only what its sources state.

Links: lane:officeLane from core's processes to a lane. Requires core 2.2.0, a pin that lags core's 2.3.0.

integration 2.3.0 448 triples

Holds no new facts, only rules about the other modules' links. It ships three source folders as one package:

  • placement: which links prove the work. vs:produces and dp:producedBy certify; every other placement, kpi:informsProcess among them, is context (EPM-DEC-001-0058).
  • authority: five evidence tiers for the 102 cited sources: process authority, MPC, U.S. refining peers, industry and regulatory sources, and generic frameworks. The best tier wins (EPM-DEC-001-0059).
  • consumer: 13 rules for what a catalog binds and an agent may answer or must refuse (EPM-DEC-001-0061).

In the crack spread's story

The rule Quote a value through its bound metric view lets an agent give the crack spread's value only through the view that dp:servesMeasure it, naming the view and adding the measure's definition, kind and what it is not. The measure's sources have tiers: the planner measure list is process authority, the MPC performance-measures evidence is MPC, and the KPI classification evidence is peers.

Requires every other module. No catalog row publishes the crack-spread measure yet; the binding is the view's dp:servesMeasure (EPM-DEC-001-0100, item 4).

How it reaches the stores

The eleven releases are the master copy, as Turtle. From them, two projections build a Neo4j property graph. The repository's pipeline.py loads a local Neo4j. The ontology-to-lpg skill's driver loads a second local Neo4j, copies it to AuraDB, writes the triples to the Databricks table workspace.epm_ontology.epm_triples, and rebuilds the graph from that table to prove it holds the whole ontology.

The planned next step links the metric views in Unity Catalog to the ontology's measures by KPI identifier, so that an agent working in Databricks can reach a measure's full context.

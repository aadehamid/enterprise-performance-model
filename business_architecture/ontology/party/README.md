# party: the decision owner's conceptual model of Customer

The `party` module turns the decision owner's conceptual data model of Customer into classes, properties and code lists (EPM-DEC-001-0067 for the sources and scope, EPM-DEC-001-0068 for the design). Its namespace is `https://w3id.org/lsc/ontology/modules/party/`. It holds definitions only: customer records stay in the systems (EPM-DEC-001-0005). The decision owner's model and other inputs are not in this repository; the definitions are derived from them, in Claude's words.

| File | What |
|---|---|
| `vocabulary.ttl` | The fifteen entity classes, 17 classes with Person and Organization (party with person and organization, external identifier, address, contact point, party role, party relationship, customer account, customer class, line of business, brand, agreement, site brand assignment, party transaction association, product, site) and the properties that link them |
| `code-lists.csv`, `build_party.py`, `code-lists.ttl` | The sixteen code lists, one row per value. Twelve describe the model (EPM-DEC-001-0068): party types, 14 party roles, 5 relationship types, 7 agreement types, 10 lines of business, 14 customer classes in 4 groups (eight of them carrying MPC's C1 to C8, the values of MPC-P06's channel dimension), site types, operating models, identifier types, address usages, contact types and transaction kinds. Four describe the systems and attributes (EPM-DEC-001-0069): system tiers, attribute categories (Create and Enrich), shared attributes and customer sourcing kinds. `--verify` fails unless `code-lists.ttl` equals a fresh build. `scripts/check.sh` runs it |
| `systems.csv`, `data-flows.csv`, `customer-sources.csv`, `attributes.csv`, `systems.ttl` | The customer's systems and data flow (EPM-DEC-001-0069): 42 systems in five tiers, with what the six core systems implement; 35 data flows; 24 customer sourcings (where a kind of customer starts, is set up or comes from); and 275 system attributes, 43 Create and 232 Enrich, each mapped to the entity it describes; 48 of them carry one of nine shared attributes, such as the SAP customer number. `build_party.py` builds `systems.ttl` from the four tables |
| `shapes.ttl` | SHACL shapes for records stated in these terms: one party per role, dated roles and class assignments, coded values from their own lists, and no class other than Person and Organization as a subclass of party, directly or through any chain of subclass links; and for the systems, data flows, sourcings and attributes (each system says what it does, each flow joins two systems and names its inputs, each attribute has a category and describes one entity or the system record). They join the Step 9 gate (EPM-DEC-001-0065) |
| `examples.ttl` | Five invented organizations, each holding several roles, plus a contact person. Test fixtures only; not loaded with the module |
| `test_party.py` | Tests: the build is current, the decided values of each list, the fifteen entity classes, the five organizations read both ways (party to roles, role to party), and SHACL accepting the examples and rejecting each kind of break |
| `test_party_systems.py` | Tests: the figures, the core systems' entities, the three matches to the system module, the origin patterns, key flows, the shared identifiers, the corrected labels, sample mappings, and the shapes |

The regression loads `vocabulary.ttl`, `code-lists.ttl` and `systems.ttl` with the release. The module is not released yet; a release needs the decision owner's approval.

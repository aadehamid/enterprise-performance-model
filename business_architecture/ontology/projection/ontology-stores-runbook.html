How the EPM ontology and the pricing demo's synthetic data reach six stores, and how to check, stop, start, purge, reload and keep in step each one. Every command runs on this Mac. No password appears on this page: each login stays in its env file.

How it fits together

Two flows feed the stores. The ontology flow starts at the process map and ends in the graph stores and a Databricks table. The demo flow starts at public market data and ends in Databricks metric views and Genie agents. Since E3 (2026-10-29) each metric-view measure that implements a kpi measure carries its KPI or OPM identifier, and definitions views read those measures' definitions from the Databricks table. Since E4 (2026-10-29) four Genie agents each read one subject area's metric views and its definitions view, and an orchestrator run from this Mac routes questions between them. Since E5 (2026-10-29) a technical graph of the demo's pipeline and its decision trail sit beside the ontology in both local Neo4j stores and AuraDB, under the label Tech, and in two Delta tables.

The ontology, in five steps

  1. The process map and each module's source files are the master copy.
  2. Each module's builder turns its sources into Turtle, and check.sh gates every change.
  3. A release freezes a module as a tagged package under business_architecture/ontology/releases/.
  4. Two projections turn the packages into a property graph. pipeline.py (run by run_local.sh) is the repository's own; the ontology-to-lpg skill's driver is the other, and it also copies the graph to AuraDB and writes the triples to Databricks.
  5. The driver then rebuilds its graph from the Databricks table, which proves the table holds the whole ontology.

The demo data, in five steps

  1. Real EIA spot prices and MPC's 10-K capacities anchor the numbers.
  2. A seeded generator writes the six source systems' rows, and EIA's weekly series, into local Postgres.
  3. DuckDB copies them to Parquet, and the Parquet files go to the idp_sbx volume.
  4. Databricks builds the replica, silver and gold tables, then six metric views and five definitions views of the ontology's measures.
  5. Four Genie agents answer questions from the metric views, each reading its definitions view (since E7, 2026-10-29, two of them also read plain tables: the refinery plans, decisions, events, EIA data and outside context, and the freight rates); an orchestrator routes a question to one or more of them. SPARQL Anything then builds a technical graph of the pipeline, which goes into Neo4j and two Delta tables (E5).

Before you start

You need these on the Mac:

  • Docker Desktop, running.
  • uv, and Java 11 or later for ROBOT.
  • ROBOT 1.9.10 at ~/epm-lpg/robot.jar, and the n10s jar in ~/epm-lpg/plugins/. The projection README's "Rerun the whole pipeline", steps 1 to 3, downloads both and gives their checksums.
  • The env files named in the table. Create the Aura and Databricks files yourself, then run chmod 600 on each.

Every tool behind the stores and the demo, with its version: the ontology guide's "The tools behind it".

The commands use two folders. Set them once per terminal:

EPM="$HOME/Dropbox/1_PROJECTS/Enterprise Performance Model"
DEMO="$EPM/demos/downstream-pricing-databricks-free"

Check what is running

docker ps --format '{{.Names}}  {{.Status}}'

All three local stores are up when the list shows epm-lpg, lpg-local-neo4j-1 and pricing-demo-sources.

Count what each store holds

Every count below reads :Resource nodes and the edges between them, the projection itself. The demo's technical graph (E5) is labelled Tech, has no edge pointing into it from the ontology, and so changes none of them; MATCH (n:Tech) RETURN count(n) counts it, 134 nodes after its load on 2026-10-29 and 142 since E6 the same day.

Pipeline Neo4j. The password is read from its file into NEO4J_PASSWORD, which docker exec -e passes to cypher-shell, and the command below names the variable, not the value, and prints no login:

set -a; . ~/epm-lpg/run.env; set +a
docker exec -e NEO4J_PASSWORD epm-lpg cypher-shell -u neo4j \
  "MATCH (n:Resource) RETURN count(n) AS nodes; MATCH (:Resource)-[r]->(:Resource) RETURN count(r) AS relationships;"

Driver Neo4j. After a full driver run its login is in the epm-rebuild file; after a run with --skip rebuild, change epm-rebuild to epm in the first line:

export NEO4J_PASSWORD=$(grep '^PASSWORD=' ~/lpg-out/epm-rebuild/neo4j-run/run.env | cut -d= -f2-)
docker exec -e NEO4J_PASSWORD lpg-local-neo4j-1 cypher-shell -u neo4j \
  "MATCH (n:Resource) RETURN count(n) AS nodes; MATCH (:Resource)-[r]->(:Resource) RETURN count(r) AS relationships;"

Postgres, the exact row count of every table in each database. Postgres quotes each table name itself (format with %I), so no name is pasted into the SQL. psql 16.10's own help describes \gexec as "execute query, then execute each value in its result" and ON_ERROR_STOP as "stop batch execution after error"; on 2026-10-26 a count of a missing table exited with status 3. The block prints count failed for any database it could not count, and ends with a non-zero status if one failed:

rc=0
for db in price_assessment price_reference reference_data_hub rightangle aspen_pims production_accounting eia_weekly decision_truth; do
  printf '%s\n' "select format('select %L, count(*) from %I.%I', '$db.' || tablename, schemaname, tablename) from pg_tables where schemaname = 'public' order by tablename \gexec" \
    | docker exec -i pricing-demo-sources psql -U demo -d "$db" -At -F ': ' -v ON_ERROR_STOP=1 \
    || { echo "count failed: $db"; rc=1; }
done
[ "$rc" -eq 0 ]

The demo in Databricks, every table and metric view with its row count:

cd "$DEMO" && uv run python -m pricing_demo.databricks counts

AuraDB: open the instance in the Aura console and run the same two queries as for the driver's Neo4j. After the reload of 2026-10-28 the copy step read back the driver's figures: 4,193 nodes and 22,142 relationships. The queries count only :Resource nodes, the projection itself; each store also holds a few nodes of its own (module tags and, locally, n10s settings), so a count of every node is a little higher.

Stop, start and reboot

Stopping keeps the data; purging removes it. A reload brings a purged store back from the repository.

Stop the local stores

docker stop epm-lpg lpg-local-neo4j-1 pricing-demo-sources

Start them again

docker start epm-lpg lpg-local-neo4j-1 pricing-demo-sources

Neo4j needs about a minute after a start. Wait for each one to accept a login before you count anything. Each block below tries for up to two minutes, prints ready or not ready, and ends with a non-zero status when it is not ready.

The pipeline's Neo4j:

set -a; . ~/epm-lpg/run.env; set +a
state="not ready"
for i in $(seq 1 24); do
  if docker exec -e NEO4J_PASSWORD epm-lpg cypher-shell -u neo4j "RETURN 1" >/dev/null 2>&1; then
    state=ready; break
  fi
  sleep 5
done
echo "$state"; [ "$state" = ready ]

The driver's Neo4j (after a run with --skip rebuild, change epm-rebuild to epm):

export NEO4J_PASSWORD=$(grep '^PASSWORD=' ~/lpg-out/epm-rebuild/neo4j-run/run.env | cut -d= -f2-)
state="not ready"
for i in $(seq 1 24); do
  if docker exec -e NEO4J_PASSWORD lpg-local-neo4j-1 cypher-shell -u neo4j "RETURN 1" >/dev/null 2>&1; then
    state=ready; break
  fi
  sleep 5
done
echo "$state"; [ "$state" = ready ]

After a reboot

  1. Start Docker Desktop, if it does not start at login.
  2. Start all three containers, whichever came back by itself (Postgres has restart: unless-stopped in the demo's compose file; the two Neo4j have no restart policy). On 2026-10-26, docker start on a container that was already running exited 0 and left it running, with the same start time: 
    docker start epm-lpg lpg-local-neo4j-1 pricing-demo-sources
  3. Wait for both Neo4j with the two blocks in Start them again.
  4. Then run the counts in Check what is running.

The cloud stores

AuraDB and Databricks need no shutdown from this Mac. Nothing here keeps them running. A Databricks SQL warehouse stops after it has been idle for the minutes its Auto Stop setting gives (Databricks, "Create a SQL warehouse", read 2026-10-26). If a query reports it stopped, start it on the SQL Warehouses page. Manage the Aura instance from the Aura console.

Reload from scratch

Reload in this order. Every reload replaces what its store held, so you need not purge first. The commands rebuild everything from the repository; nothing is lost that the repository does not hold.

1. Postgres: the seven source databases and decision_truth

cd "$DEMO"
docker compose -f docker/docker-compose.yml up -d
uv run python -m pricing_demo.load_postgres

load_postgres drops, recreates and fills each table in one transaction per database, then checks the row counts.

2. Databricks: the demo catalog

cd "$DEMO"
uv run python -m pricing_demo.replicate          # Postgres to Parquet, with DuckDB
uv run python -m pricing_demo.databricks setup   # catalog DEMO_CATALOG as given, or idp_sbx when it is unset; schemas, volume
uv run python -m pricing_demo.databricks upload  # Parquet to the volume
uv run python -m pricing_demo.databricks build   # replica, silver, gold, metric views, definitions views, empty tech_graph tables
uv run python -m pricing_demo.genie              # the four Genie agents
uv run python -m pricing_demo.databricks counts  # check the row counts

The Genie step updates an agent that already exists by its title, so running it again makes no duplicates.

3. The pipeline's Neo4j

cd "$EPM/business_architecture/ontology/projection"
./run_local.sh --keep

It builds, reasons with ROBOT, loads and checks the graph, and leaves epm-lpg running with a new password in ~/epm-lpg/run.env. It ends with projection done. Then check that git shows no changed file. A changed projection-report.json or manifest means the inputs changed and belongs in a pull request.

4. The driver: its Neo4j, AuraDB and Databricks epm_triples

cd ~/.agents/skills/ontology-to-lpg/scripts
uv run --no-project --with rdflib python3 run_projection.py \
  --config "$EPM/business_architecture/ontology/projection/skill-run/epm-run.json"

One run does all of it, in this order:

  1. It projects the releases.
  2. It loads and checks its local Neo4j.
  3. It replaces what AuraDB holds with a copy.
  4. It writes epm_triples in one CREATE OR REPLACE.
  5. It rebuilds the graph from that table into a fresh local Neo4j, which it keeps.

It ends with every step passed. It takes about ten minutes.

  • Add --plan to list the steps without running them.
  • Add --skip databricks to leave the table as it is.
  • After --skip rebuild, the kept graph's login is in ~/lpg-out/epm/neo4j-run/run.env instead of the epm-rebuild one.
When it is doneEvery store holds the newest releases again. Run the counts in Check what is running.

5. The demo's technical graph

Steps 3 and 4 empty their Neo4j stores and AuraDB, so the technical graph goes back in after them. Steps 1 and 2 must have run, and the Databricks build leaves its two Delta tables empty until the sync fills them:

cd "$DEMO"
uv run --group graph python -m pricing_demo.tech_graph collect   # live facts, checks, lineage
uv run --group graph python -m pricing_demo.tech_graph build     # SPARQL Anything -> graph/*.ttl
uv run --group graph python -m pricing_demo.tech_graph load      # both local Neo4j stores and AuraDB
uv run --group graph python -m pricing_demo.tech_graph sync      # Neo4j -> idp_sbx.tech_graph

The load stops if a store's :Resource counts change, or if an edge to the ontology finds no node.

Keeping the stores in step

The guide's "The plan to close it, not built yet" lists the work that would make these checks run by themselves (#455).

Since 2026-10-29 each ontology store says which release set it was loaded from, so a new release shows which stores are behind. sync_stores.py, in the projection folder, does the checking and the reloading with the commands above.

What each store records

A marker with the catalog's datasets (their count and a digest of their IRIs, from releases/catalog.ttl), the projection's input fingerprint (from projection-manifest.json), the counts the store held when it was marked, the time and the commit. In the three Neo4j stores the marker is a node labelled EpmStoreMarker, never Resource, so the projection's counts, hash and round trip do not see it. In Databricks it is a row in epm_store_markers, beside epm_triples.

A store is marked only after a check against the repository: the pipeline's graph must give the committed report's hash and counts; the driver's Neo4j and AuraDB must hold the projection's nodes and the driver report's relationships; epm_triples must hold every module's newest release. A pipeline reload deletes every node, the marker with them, so a store reloaded by hand reads as unmarked until it is marked again.

cd "$EPM/business_architecture/ontology/projection"
uv run -q --with rdflib --with pyshacl --with neo4j --with databricks-sql-connector python sync_stores.py mark --store pipeline --store driver --store aura --store databricks

The drift check

It compares each marker with main's newest catalog and manifest (fetch main first; --ref names another ref) and each store's live count with its marker. Each store is current, behind (marked from another release set), changed (its count moved since it was marked), unmarked, or unreachable (the store could not be read: no connection, no login file or a missing table, for example; the error's name follows the word). It exits non-zero unless every store is current.

uv run -q --with rdflib --with pyshacl --with neo4j --with databricks-sql-connector python sync_stores.py check

On 2026-10-29, after the four markers were written, every store read as current at commit 4d1e675b: the pipeline graph with 4,193 nodes and 21,767 relationships and its hash unchanged, the driver's Neo4j and AuraDB with 4,193 and 22,142, and epm_triples with 40,169 rows.

sync_stores.py sync

It runs the drift check, then reloads what is not current: the pipeline graph with run_local.sh --keep (Reload, step 3), and the driver's Neo4j with a driver run that skips its copy, databricks and rebuild steps, so that graph comes from the repository rather than back from epm_triples. AuraDB and Databricks reload only with --cloud, through the full driver run (step 4), which reloads the driver's Neo4j too. Then it loads the technical graph back into each Neo4j store it reloaded (step 5) and marks those stores. --dry-run prints the commands and runs nothing. Only --dry-run has run so far: the reload path has not run live, so its first real reload is its test. Run it from a checkout of main: it marks what the working tree's catalog says, while the drift check reads main's. The driver is found in $EPM_SKILLS, by default ~/.agents/skills.

uv run -q --with rdflib --with pyshacl --with neo4j --with databricks-sql-connector python sync_stores.py sync --dry-run
uv run -q --with rdflib --with pyshacl --with neo4j --with databricks-sql-connector python sync_stores.py sync --cloud

The release-tag workflow

.github/workflows/sync-stores.yml runs on every release tag (kpi-v1.3.0, say) and by hand. It runs the full driver for AuraDB and Databricks on a GitHub runner and marks both. It is inactive until these repository secrets exist; without all of them its first step ends the job with a notice and nothing else runs:

SecretWhat it holds
EPM_AURA_URI, EPM_AURA_USERNAME, EPM_AURA_PASSWORDThe AuraDB login, as in ~/.config/neo4j/aura.env
EPM_DATABRICKS_HOST, EPM_DATABRICKS_TOKEN, EPM_DATABRICKS_HTTP_PATHThe Databricks login, as in ~/.config/databricks/epm.env; the workflow writes the catalog workspace and schema epm_ontology itself

Add them under the repository's Settings, Secrets and variables, Actions. The workflow has not run with secrets yet, so its first run is its test. It checks out the skills repository at a pinned commit, so a later change to the driver doesn't reach it until the pin moves. It doesn't load the technical graph back into AuraDB, which the driver's copy step empties: after it runs, load it from the laptop with tech_graph load --store aura (Reload, step 5).

Purge

Read this first.A purge cannot be undone. The data comes back only by reloading, which rebuilds what these commands remove from the repository. The local and Databricks commands below remove only what the demo or the projection created; the AuraDB command empties the whole Aura database, which holds only these test runs (skill-run/README.md). On 2026-10-26 the decision owner asked to keep these stores loaded. Purge only when you mean to.

-v also removes each container's data volume. The next run_local.sh --keep or driver run creates a new container with a new password.

Local Postgres

This deletes the volume pricing-demo-pgdata.down -v removes the named volume that the compose file declares, and the eight databases go with it.
cd "$DEMO"
docker compose -f docker/docker-compose.yml down -v

To remove the container but keep the data, run the same command without -v.

AuraDB

In the Aura console's query tool, run this as one statement. In Neo4j Browser, put :auto in front of it, because CALL { … } IN TRANSACTIONS "is only allowed in implicit transactions" (Neo4j Cypher Manual 25, "CALL subqueries in transactions", read 2026-10-26):

MATCH (n) CALL (n) { DETACH DELETE n } IN TRANSACTIONS OF 10000 ROWS

This empties the database and keeps the instance. The next driver run fills it again.

Databricks

The ontology triples: run this in the Databricks SQL editor.

DROP TABLE IF EXISTS workspace.epm_ontology.epm_triples;

The demo: its own purge step drops exactly the tables and views its SQL files create, then its volume, then its fourteen schemas without CASCADE (tech_graph since E5). A schema that still holds anything the demo did not create is not dropped: without CASCADE, DROP SCHEMA runs as RESTRICT, which "restricts dropping a non-empty schema and is enabled by default" (Databricks, "DROP SCHEMA", read 2026-10-26), so that statement fails and the step stops. Run it once without --yes to see the statements and the catalog it will use, then with --yes to drop:

cd "$DEMO"
uv run python -m pricing_demo.databricks purge         # lists the statements; drops nothing
uv run python -m pricing_demo.databricks purge --yes   # drops them

The AuraDB login the demo wrote for its Databricks test sits in the secret scope epm-neo4j, outside the catalog. Delete the scope with uv run python -c "from pricing_demo.config import databricks_env; from databricks.sdk import WorkspaceClient; e = databricks_env(); WorkspaceClient(host=e['DATABRICKS_HOST'], token=e['DATABRICKS_TOKEN']).secrets.delete_scope('epm-neo4j')". The probe it ran, aura_probe.py, sits in your workspace folder pricing-demo; delete that folder in the workspace browser.

The Genie agents are not in the catalog. Delete Crack Spread Price Analytics, Executive Summary KPIs Analytics, Pricing and Market Margin Analytics and Refinery Operations Analytics in Genie, or leave them: the next genie step updates them in place.

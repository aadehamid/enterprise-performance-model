How it fits together

Two flows feed the stores. The ontology flow starts at the process map and ends in the graph stores and a Databricks table. The demo flow starts at public market data and ends in Databricks metric views and Genie agents. Since E3 (2026-10-29) each metric-view measure that implements a kpi measure carries its KPI or OPM identifier, and definitions views read those measures' definitions from the Databricks table. Since E4 (2026-10-29) four Genie agents each read one subject area's metric views and its definitions view, and an orchestrator run from this Mac routes questions between them. Since E5 (2026-10-29) a technical graph of the demo's pipeline and its decision trail sit beside the ontology in the local Neo4j and AuraDB, under the label Tech, and in two Delta tables.

The ontology, in five steps

  1. The process map and each module's source files are the master copy.
  2. Each module's builder turns its sources into Turtle, and check.sh gates every change.
  3. A release freezes a module as a tagged package under business_architecture/ontology/releases/.
  4. One loader, the ontology-to-lpg skill's driver, turns the packages into a property graph in the local Neo4j. It also copies that graph to AuraDB, and it writes all three graphs of each package to Jena and to Databricks. In CI, pipeline.py build --verify checks the same inputs with no database.
  5. The driver then rebuilds the local graph from the Databricks table, which proves the table holds the whole ontology.

The demo data, in five steps

  1. Real EIA spot prices and MPC's 10-K capacities anchor the numbers.
  2. A seeded generator writes the six source systems' rows, and EIA's weekly series, into local Postgres.
  3. DuckDB copies them to Parquet, and the Parquet files go to the idp_sbx volume.
  4. Databricks builds the replica, silver and gold tables, then six metric views and five definitions views of the ontology's measures.
  5. Four Genie agents answer questions from the metric views, each reading its definitions view (since E7, 2026-10-29, two of them also read plain tables: the refinery plans, decisions, events, EIA data and outside context, and the freight rates); an orchestrator routes a question to one or more of them. SPARQL Anything then builds a technical graph of the pipeline, which goes into Neo4j and two Delta tables (E5).

What each store holds

Each module package has three Turtle files. <module>.ttl is the content. shapes.ttl is the rules. catalog.ttl is the DCAT release record: the dataset, its version, its issue date and its distributions. ../MODULES.md gives each module's purpose and the files each package is built from.

StoreContent, <module>.ttlRules, shapes.ttlRelease record, catalog.ttl
Jena and Databricks epm_triplesAll, one named graphAll, one named graphAll, one named graph
Local Neo4j and AuraDBAll, with no selective projectionNot nodes. They validate the release: pySHACL before the load, n10s in the graph at the loadNot in full: one ModuleRelease node per module

Neo4j holds all the content so that the round trip keeps proving 0 lost and 0 added. A selective projection would lose that proof.

A package may also carry graphs of its own beside the three files. Only the logical-model module does, and main holds no package of it, so main's stores hold none (EPM-DEC-001-0113, amendment "the stores"). When the newest releases hold the module, as a share release's do, projection/logical_models.py load puts each model's ER Studio export and annotation layer into Jena and epm_triples as named graphs of their own, <version IRI>/<slug>.erstudio and <version IRI>/<slug>.layer, and each model in full into the local Neo4j and AuraDB as a subgraph labelled LogicalModel, never Resource: its entities with their names and descriptions, their attributes and keys, the relationships between them, and an edge from each entity to each ontology node its layer names. The projection loads the module's vocabulary like every package's.

A ModuleRelease node holds module, version, version_iri, ontology, download_url, conforms, in_graph_constraints, violations, shapes_sha256, projection_version and loaded_at. conforms, in_graph_constraints and violations describe the whole load, because the shapes run over every module together. A DESCRIBES relationship links the node to its module's owl__Ontology node. The node has no Resource label, so the hash, the counts, the module tags and the round trip do not read it, and no field enters a hash. To read the records:

MATCH (r:ModuleRelease)-[:DESCRIBES]->(o) RETURN r.module, r.version, r.conforms, r.violations, r.loaded_at, o.uri ORDER BY r.module

Two labels on a class do not mean two nodes. A class is one node with owl__Class, from its own triple, and n4sch__Class, from n10s's ontology import. 46 classes carry both. Count classes with one of them.

Count what each store holds

Every count below reads :Resource nodes and the edges between them, the projection itself. The demo's technical graph (E5) is labelled Tech, has no edge pointing into it from the ontology, and so changes none of them; MATCH (n:Tech) RETURN count(n) counts it, 134 nodes after its load on 2026-10-29 and 142 since E6 the same day.

The local Neo4j. The password is read from its file into NEO4J_PASSWORD, which docker exec -e passes to cypher-shell, and the command below names the variable, not the value, and prints no login. After a full driver run its login is in the epm-rebuild file; after a run with --skip rebuild, change epm-rebuild to epm in the first line:

export NEO4J_PASSWORD=$(grep '^PASSWORD=' ~/lpg-out/epm-rebuild/neo4j-run/run.env | cut -d= -f2-)
docker exec -e NEO4J_PASSWORD lpg-local-neo4j-1 cypher-shell -u neo4j \
  "MATCH (n:Resource) RETURN count(n) AS nodes; MATCH (:Resource)-[r]->(:Resource) RETURN count(r) AS relationships;"

Jena. The check compares its graph names and each graph's triple count with the release files, and reads empty after a restart:

cd "$EPM/business_architecture/ontology/projection"
uv run -q --with rdflib --with pyshacl --with neo4j --with databricks-sql-connector python sync_stores.py check --store jena

Postgres, the exact row count of every table in each database. Postgres quotes each table name itself (format with %I), so no name is pasted into the SQL. psql 16.10's own help describes \gexec as "execute query, then execute each value in its result" and ON_ERROR_STOP as "stop batch execution after error"; on 2026-10-26 a count of a missing table exited with status 3. The block prints count failed for any database it could not count, and ends with a non-zero status if one failed:

rc=0
for db in price_assessment price_reference reference_data_hub rightangle aspen_pims production_accounting eia_weekly decision_truth; do
  printf '%s\n' "select format('select %L, count(*) from %I.%I', '$db.' || tablename, schemaname, tablename) from pg_tables where schemaname = 'public' order by tablename \gexec" \
    | docker exec -i pricing-demo-sources psql -U demo -d "$db" -At -F ': ' -v ON_ERROR_STOP=1 \
    || { echo "count failed: $db"; rc=1; }
done
[ "$rc" -eq 0 ]

The demo in Databricks, every table and metric view with its row count:

cd "$DEMO" && uv run python -m pricing_demo.databricks counts

AuraDB: open the instance in the Aura console and run the same two queries as for the local Neo4j. After the reload of 2026-10-28 the copy step read back 4,193 nodes and 22,142 relationships. The queries count only :Resource nodes, the projection itself; each store also holds a few nodes of its own (module tags, release records and, locally, n10s settings), so a count of every node is a little higher.

Stop, start and reboot

Stopping keeps the data; purging removes it. A reload brings a purged store back from the repository.

Stop the local stores

docker stop lpg-local-neo4j-1 epm-jena-fuseki-1 pricing-demo-sources

Start them again

docker start lpg-local-neo4j-1 epm-jena-fuseki-1 pricing-demo-sources

Stopping keeps the data of Neo4j and Postgres. Jena's dataset is in memory, so it comes back empty: reload it with the driver's jena step, through sync_stores.py sync (Keeping the stores in step).

Neo4j needs about a minute after a start. Wait for it to accept a login before you count anything. The block below tries for up to two minutes, prints ready or not ready, and ends with a non-zero status when it is not ready.

The local Neo4j (after a run with --skip rebuild, change epm-rebuild to epm):

export NEO4J_PASSWORD=$(grep '^PASSWORD=' ~/lpg-out/epm-rebuild/neo4j-run/run.env | cut -d= -f2-)
state="not ready"
for i in $(seq 1 24); do
  if docker exec -e NEO4J_PASSWORD lpg-local-neo4j-1 cypher-shell -u neo4j "RETURN 1" >/dev/null 2>&1; then
    state=ready; break
  fi
  sleep 5
done
echo "$state"; [ "$state" = ready ]

After a reboot

  1. Start Docker Desktop, if it does not start at login.
  2. Start all three containers, whichever came back by itself (Postgres has restart: unless-stopped in the demo's compose file; Neo4j and Jena have no restart policy). On 2026-10-26, docker start on a container that was already running exited 0 and left it running, with the same start time: 
    docker start lpg-local-neo4j-1 epm-jena-fuseki-1 pricing-demo-sources
  3. Wait for Neo4j with the block in Start them again.
  4. Reload Jena, which a reboot empties, with sync_stores.py sync (Keeping the stores in step).
  5. Then run the counts in Check what is running.

3. Retire the old local Neo4j, once

An earlier setup kept a second local Neo4j, in an older form. Remove it once:

docker rm -f -v epm-lpg

4. The driver: the local Neo4j, Jena, AuraDB and Databricks epm_triples

cd ~/.agents/skills/ontology-to-lpg/scripts
uv run --no-project --with rdflib python3 run_projection.py \
  --config "$EPM/business_architecture/ontology/projection/skill-run/epm-run.json"

One run does all of it, in this order:

  1. It projects the releases.
  2. It empties the local Neo4j, then loads and checks it.
  3. It writes one ModuleRelease node per module.
  4. It replaces what AuraDB holds with a copy, and writes the same records there.
  5. It loads all three graphs of each package into Jena, proves the round trip, and leaves Jena running. It replaces the Fuseki already on port 13031, because the run configuration names the same compose project, epm-jena.
  6. It writes epm_triples in one CREATE OR REPLACE.
  7. It rebuilds the graph from that table into a fresh local Neo4j, which it keeps, and copies that to AuraDB.

It ends with every step passed. It takes about ten minutes.

  • Add --plan to list the steps without running them.
  • Add --skip databricks to leave the table as it is.
  • After --skip rebuild, the kept graph's login is in ~/lpg-out/epm/neo4j-run/run.env instead of the epm-rebuild one.

Then take the run's result into the repository. Check what git shows: a changed projection-report.json, manifest or inferred.nt means the inputs changed and belongs in a pull request.

cd "$EPM/business_architecture/ontology/projection"
uv run -q --with rdflib --with pyshacl python pipeline.py record --run ~/lpg-out/epm

Keeping the stores in step

Nothing runs these checks by itself: sync_stores.py check is a written step of each release, which is done only when every store reads current, ontology and technical graph, and each logical model's lm: line when the releases hold the module (EPM-DEC-001-0112, amendment of 2026-11-02 (later), item 3). The guide's "The plan to close it" says what runs now and what is left (#455).

Since 2026-10-29 each ontology store says which release set it was loaded from, so a new release shows which stores are behind. sync_stores.py, in the projection folder, does the checking and the reloading with the commands above.

What each store records

A marker with the catalog's datasets (their count and a digest of their IRIs, from releases/catalog.ttl), the projection's input fingerprint (from projection-manifest.json), the counts the store held when it was marked, the time and the commit. In the local Neo4j and AuraDB the marker is a node labelled EpmStoreMarker, never Resource, so the projection's counts, hash and round trip do not see it. In Databricks it is a row in epm_store_markers, beside epm_triples. Jena has no marker: its named graphs are version IRIs, so the check compares its graph names and each graph's triple count with the release files. The technical graph has a marker of its own, a digest of the graph files it was loaded from: tech_graph load writes a TechGraphMarker node in each Neo4j store and a named graph in Jena, in the same transaction or request as the graph, and tech_graph sync writes the row tech_graph in epm_store_markers for the Delta copy.

A store is marked only after a check against the repository: the local Neo4j and AuraDB must hold the committed report's counts and one release record for each newest release; epm_triples must hold exactly the graphs of the newest releases, each with as many rows as the release files have triples. A driver load deletes every node, the marker with them, so a store reloaded by hand reads as unmarked until it is marked again. The store's name in these commands is driver for the local Neo4j.

cd "$EPM/business_architecture/ontology/projection"
uv run -q --with rdflib --with pyshacl --with neo4j --with databricks-sql-connector python sync_stores.py mark --store driver --store aura --store jena --store databricks

The drift check

It compares each marker with main's newest catalog and manifest (fetch main first; --ref names another ref) and each store's live count with its marker. Jena and Databricks are also judged per named graph against the release files: a graph that is missing, extra or of another size reads changed, with the graph named, even when Databricks' total holds. Each store is current, behind (marked from another release set), changed (its count moved since it was marked), unmarked, or unreachable (the store could not be read: no connection, no login file or a missing table, for example; the error's name follows the word). Jena reads current, behind (other graphs than the newest releases), changed (the same graphs with another triple count) or empty (a restart emptied it). A second line per store, tech:<store>, judges the technical graph the same way from its marker: current, behind (loaded from other graph files), changed (a Neo4j store's Tech count moved, or the content it holds differs from the graph files although its marker matches: the check compares a fingerprint of the Tech nodes and edges, Jena's two graphs or the Delta tables with the files'), unmarked or unreachable. When the newest releases hold the logical-model module, a third line per Neo4j store, lm:<store>, judges the LogicalModel subgraph the same way, from its LogicalModelMarker (a digest of the model files) and a fingerprint of its nodes and edges, and the models' named graphs count with the release graphs on Jena's and Databricks' lines; main holds no such module, so it prints no lm: line. It exits non-zero unless every line is current.

uv run -q --with rdflib --with pyshacl --with neo4j --with databricks-sql-connector python sync_stores.py check

On 2026-10-29, after the four markers were written, every store read as current at commit 4d1e675b: the pipeline graph with 4,193 nodes and 21,767 relationships and its hash unchanged, the driver's Neo4j and AuraDB with 4,193 and 22,142, and epm_triples with 40,169 rows. 2026-11-01: the standard is now one local Neo4j, and the count 21,767 is the part of its 22,142 relationships that comes from the releases' triples.

sync_stores.py sync

It runs the drift check, then reloads what is not current. The local Neo4j and Jena reload with a driver run that skips its copy, databricks and rebuild steps, so that graph comes from the repository rather than back from epm_triples. Jena alone reloads with the driver's jena step, which touches no Neo4j. AuraDB and Databricks reload only with --cloud, through the full driver run (step 4), which reloads the local Neo4j and Jena too. A run that loads the local Neo4j then takes its result into the repository with pipeline.py record. Then it loads the technical graph into each store it reloaded and each whose technical-graph marker is not current (step 5), runs tech_graph sync when Databricks was reloaded or its copy is not current, runs logical_models.py load last on each store it reloaded and each whose lm: line is not current, when the releases hold the logical-model module, and marks the stores it reloaded. --dry-run prints the commands and runs nothing. Only --dry-run has run so far: the reload path has not run live, so its first real reload is its test. Run it from a checkout of main: it marks what the working tree's catalog says, while the drift check reads main's. The driver is found in $EPM_SKILLS, by default ~/.agents/skills.

The release-tag workflow

.github/workflows/sync-stores.yml runs on every release tag (kpi-v1.3.0, say) and by hand. It runs the full driver for AuraDB and Databricks on a GitHub runner, loads the technical graph into AuraDB and copies it to Delta, loads a release's logical models into both when the releases hold the module (never in main), marks both and runs the drift check on them. It runs on no timer. It is inactive until these repository secrets exist; without all of them its first step ends the job with a notice and nothing else runs:

It checks out the skills repository at a pinned commit, so a later change to the driver doesn't reach it until the pin moves. The driver's copy step empties the technical graph from AuraDB, so the workflow loads it back with tech_graph load --store aura.

AuraDB

In the Aura console's query tool, run this as one statement. In Neo4j Browser, put :auto in front of it, because CALL { … } IN TRANSACTIONS "is only allowed in implicit transactions" (Neo4j Cypher Manual 25, "CALL subqueries in transactions", read 2026-10-26):

MATCH (n) CALL (n) { DETACH DELETE n } IN TRANSACTIONS OF 10000 ROWS

This empties the database and keeps the instance. The next driver run fills it again.

Databricks

The ontology triples: run this in the Databricks SQL editor.

DROP TABLE IF EXISTS workspace.epm_ontology.epm_triples;

The demo: its own purge step drops exactly the tables and views its SQL files create, then its volume, then its fourteen schemas without CASCADE (tech_graph since E5). A schema that still holds anything the demo did not create is not dropped: without CASCADE, DROP SCHEMA runs as RESTRICT, which "restricts dropping a non-empty schema and is enabled by default" (Databricks, "DROP SCHEMA", read 2026-10-26), so that statement fails and the step stops. Run it once without --yes to see the statements and the catalog it will use, then with --yes to drop:

cd "$DEMO"
uv run python -m pricing_demo.databricks purge         # lists the statements; drops nothing
uv run python -m pricing_demo.databricks purge --yes   # drops them

The AuraDB login the demo wrote for its Databricks test sits in the secret scope epm-neo4j, outside the catalog. Delete the scope with uv run python -c "from pricing_demo.config import databricks_env; from databricks.sdk import WorkspaceClient; e = databricks_env(); WorkspaceClient(host=e['DATABRICKS_HOST'], token=e['DATABRICKS_TOKEN']).secrets.delete_scope('epm-neo4j')". The probe it ran, aura_probe.py, sits in your workspace folder pricing-demo; delete that folder in the workspace browser.

The Genie agents are not in the catalog. Delete Crack Spread Price Analytics, Executive Summary KPIs Analytics, Pricing and Market Margin Analytics and Refinery Operations Analytics in Genie, or leave them: the next genie step updates them in place.

When something fails

What you seeWhyWhat to do
Neo4j does not print Started.The Docker disk is usually full.Check it with docker system df. Then free space: run docker builder prune and docker image prune, or remove volumes you know you do not need. Do not remove pricing-demo-pgdata.
docker compose up (Neo4j) exited 1 from the driverA container from an earlier run still holds the lpg-local name.Remove it with the driver's purge command above, then run again.
the run stopped on a driver or file error (ClientError)A query failed inside the load. On 2026-10-26 the cause was an apostrophe in an sh:message, which n10s writes into its Cypher unescaped. Since personal-agent-skills #72, the driver leaves such a message out.Update the skills checkout. If the error comes back, the n10s query text is in the Neo4j logs.
A login is refusedEach run writes a new password, and an old env file holds the old one.Use the file the table names for that store. After a full driver run, the epm-rebuild file is the current one; after a run with --skip rebuild, the epm file is.
The demo's scripts cannot reach DatabricksThe token in the env file has expired.Make a new personal access token in Databricks, and put it in ~/.config/databricks/epm.env.

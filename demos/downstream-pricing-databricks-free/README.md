# Downstream pricing demo: synthetic data in Databricks Free Edition

This demo rebuilds the pricing assets the ontology binds its pricing measures to (EPM-DEC-001-0097) in a Databricks Free Edition workspace, from real public data where it exists and synthetic data where it does not. It covers six source systems and EIA's weekly public data in Postgres (plus a hidden database of decision dossiers the pipeline never replicates), DuckDB replication, the replica layer, a silver star schema, gold tables, six metric views, five views of the ontology's measure definitions, four Genie agents and an orchestrator that routes questions between them. Every object the shared `idp_sbx` asset also has keeps its name and columns, except the replica schemas, which follow the source databases' names since 2026-10-28 (see "The source systems"), so the ontology's walk from a measure to its metric view works here. The tables added on 2026-10-28 for the three-year extension (process units, freight, the event table, EIA's weekly data) and for the decision trail (plan versions, the decision log and its evidence) have no counterpart in the shared asset; their names follow its style. So do the outside-context tables E6 added on 2026-10-29: real public events from Parallel Decisions, labelled observed, inferred or unknown. Every price row says whether it is real, spot-anchored or synthesized. The design choices are in EPM-DEC-001-0102.

The scenario is the decision owner's executive briefings for October 2026, in [SCENARIO.md](SCENARIO.md): diesel scarcity, Hurricane Isaias, a freight spike that closes arbitrage, and the G7 stock release. It drives only the synthesized parts.

## The pipeline

```
Parallel Decisions API (real public events)  -> data/parallel/*.json, one cached response per call   pricing_demo/outside.py
  -> the generator lands them in reference_data_hub: external_event, forward_scan, external_citation
Postgres, one database per source system (the exe.dev VM through an SSH tunnel; the local Docker container is the fallback)
  -> DuckDB replication: out/replica/<system>/<table>.parquet, with _change_ts and _replicated_at
  -> Unity Catalog volume idp_sbx.replica_landing.raw
  -> replica tables        idp_sbx.replica_<system>.*                         sql/02_replica.sql
  -> silver star schema    idp_sbx.silver_mdm_core.* (dims), silver_udm_core.* (facts)   sql/03_silver.sql
  -> gold                  idp_sbx.gold_commercial_core.*                     sql/04_gold.sql
  -> metric views          idp_sbx.semantic_sem_commercial.*                  sql/05_metric_views.sql
  -> definitions views     idp_sbx.ontology_definitions.*, from epm_triples   sql/06_definitions.sql
  -> Genie agents          Crack Spread Price Analytics; Executive Summary KPIs Analytics;     genie/
                          Pricing and Market Margin Analytics; Refinery Operations Analytics
  -> orchestrator          routes a question to the Genie agents, run from this machine     pricing_demo/supervisor.py
  -> technical graph       SPARQL Anything over the SQL, the run commands and the live facts -> Neo4j
                           (both local stores and AuraDB, label Tech) -> idp_sbx.tech_graph.*   pricing_demo/tech_graph.py, sparql/
```

## Run it

You need Docker, [uv](https://docs.astral.sh/uv/), and a Databricks Free Edition workspace with a personal access token. Every tool the demo uses, with its version, is in the ontology guide's "The tools behind it" (`business_architecture/ontology/epm-ontology-guide.html#tools`). Copy `.env.example` to `.env` and fill it in; the scripts also read `~/.config/databricks/epm.env`. They never print a secret. To stop, restart, purge or reload the demo's stores together with the ontology's, see `business_architecture/ontology/projection/ontology-stores-runbook.html`.

```bash
cd demos/downstream-pricing-databricks-free
docker compose -f docker/docker-compose.yml up -d          # the seven source databases and the hidden decision_truth
# A volume created before 2026-10-28 holds the old database names. Rename them once: the postgres image runs
# docker/init/ only on an empty data directory (hub.docker.com/_/postgres, "Initialization scripts", read 2026-10-28).
#   for p in mips:price_assessment mpr:price_reference kittyhawk:reference_data_hub ctrm:rightangle planning:aspen_pims prodacct:production_accounting; do
#     docker exec pricing-demo-sources psql -U demo -d postgres -c "ALTER DATABASE ${p%%:*} RENAME TO ${p##*:}"; done
#   docker exec pricing-demo-sources psql -U demo -d postgres -c "CREATE DATABASE eia_weekly"   # the seventh, since E1
#   docker exec pricing-demo-sources psql -U demo -d postgres -c "CREATE DATABASE decision_truth"   # the hidden dossiers, since E2
uv sync
uv run python -m pricing_demo.load_postgres                # generate and load the source tables
uv run python -m pricing_demo.replicate                    # Postgres -> Parquet with DuckDB
uv run python -m pricing_demo.databricks setup             # catalog idp_sbx (or DEMO_CATALOG), schemas, volume
uv run python -m pricing_demo.databricks upload            # Parquet -> the volume
uv run python -m pricing_demo.databricks build             # replica, silver, gold, metric views, definitions views, empty tech_graph tables
uv run python -m pricing_demo.genie                        # the four Genie agents
uv run python -m pricing_demo.supervisor describe          # each agent's description, built from epm_triples
uv run python -m pricing_demo.supervisor setup             # try the Supervisor Agent (Free Edition refuses it)
uv run python -m pricing_demo.supervisor ask "<question>"  # route a question through the orchestrator
uv run python -m pricing_demo.aura_test                    # can Databricks reach AuraDB? secret scope epm-neo4j, one probe job
uv run --group outside python -m pricing_demo.outside plan     # the Parallel Decisions calls each step needs, and how many are cached
uv run --group outside python -m pricing_demo.outside run --step events   # then monthly, diagnosis, forward; a cached call is never sent again
uv run --group graph python -m pricing_demo.tech_graph collect   # live facts, data-quality checks, designed against observed lineage
uv run --group graph python -m pricing_demo.tech_graph build     # SPARQL Anything: the technical graph and the decision trail, graph/*.ttl
uv run --group graph python -m pricing_demo.tech_graph load      # Tech nodes into both local Neo4j stores and AuraDB
uv run --group graph python -m pricing_demo.tech_graph sync      # Neo4j -> idp_sbx.tech_graph.tech_graph_nodes and tech_graph_edges
uv run --group graph python -m pricing_demo.tech_graph walk      # one Cypher walk from a gold table to the measures it implements
uv run python -m pricing_demo.databricks counts            # row counts
uv run python -m pricing_demo.databricks purge             # list what a purge drops; --yes drops it
uv run --with pytest python -m pytest -q tests             # offline tests
```

Postgres listens only on this machine (127.0.0.1:55432), with the throwaway login `demo`. To move the source databases to another host, change `SOURCE_PG_DSN`; nothing else names the host. Since 2026-10-28 the source databases (seven since the three-year extension, with the hidden `decision_truth` beside them) also run on an exe.dev VM, `databases.exe.xyz`, where Postgres listens only on the VM's localhost. Open a tunnel and leave it running, `ssh -N -L 127.0.0.1:5433:127.0.0.1:5432 databases.exe.xyz`, then set `SOURCE_PG_DSN=postgresql://demo:<password>@127.0.0.1:5433` in `.env`. The VM's `demo` login has its own generated password, kept only in the local `.env`. The local container stays as the fallback.

Every replication run is a full snapshot: the downstream layers replace their contents from it. The run writes `out/replica/manifest.json` with each table's rows only after every table is there and not empty; `upload` refuses a replica that does not match its manifest, and `build` checks each replica table's rows and its `_replicated_at` against the manifest, so a volume still holding an earlier run's files fails, and that every silver and gold table, metric view and definitions view exists and holds rows. Each source database loads in one transaction. Databricks Free Edition limits outbound internet to trusted domains, so the replication pushes from the machine that can reach Postgres rather than letting Databricks pull.

```cypher

OPTIONAL MATCH (agent:Tech:GenieAgent)-[:BINDS]->(view)
RETURN gold.name AS gold, view.name AS metric_view, m.uri AS measure, m.skos__prefLabel AS label,

```

### The outside context (E6, 2026-10-29)

E6 adds real public events beside the demo's synthetic data (use cases 19 to 21). `pricing_demo/outside.py` asks Parallel's Decisions API typed questions and keeps each response in `data/parallel/`, so the generator builds the tables from that cache and a rerun sends nothing. Each call sends its context in `state` and named questions in `questions`, and the response holds a typed answer per question and the citations the call drew on (Parallel, "Decisions API quickstart", docs.parallel.ai/decisions/decisions-quickstart, read 2026-10-28). The code calls `POST /v1/decisions` through the parallel-web 1.3.7 SDK's generic `client.post`, which keeps its authentication, retries and typed errors; the SDK has no Decisions resource of its own. The key is read from the environment, the demo's `.env` or `~/.config/parallel/api.env`, and never printed.

The demo asks two question types, as Typesafe defines them ("Noul" and "Choice", docs.typesafe.ai, read 2026-10-28): a noul gives one probability that a condition is true, and a choice gives a probability for each option and a confidence from their spread. A noul at 0.7 or more reads yes and at 0.3 or less no, Typesafe's suggested starting thresholds; the middle reads uncertain and goes to a person. Answers about the past are labelled observed (a yes or no noul), inferred (a choice with a confidence of 0.3 or more, the demo's floor) or unknown (a refusal, an uncertain noul or a weaker choice). Every forward answer is inferred or unknown, never observed.

The calls ran on 2026-10-29: one smoke call, 9 for the scenario's events, 108 for the monthly scan (3 regions x 36 months), 10 for the decision diagnoses and 9 for the forward look, 137 in all, each with 10 citations. Parallel prices the Decisions API at "$1 per 1,000 calls" (Parallel, "Introducing the Parallel Decisions API", 2026-10-25), so about $0.14. `parallel-cli balance get` read $24.99 before the first call, still $24.99 just after the last, and $24.86 once the charges had posted, later that day: $0.13 spent. What came back:
- The scenario's events: 6 confirmed, Hurricane Isaias uncertain (0.67), and the two scenario turnarounds not found, as they should be, since they are not MPC's schedule.
- The monthly scan: of 324 answers, 170 observed, 56 inferred and 98 unknown. The margin driver most often named was crude supply (39 of 108 region-months), then weather (33).
- The diagnoses: weather for 7 of the 10 decisions, policy for D06, logistics for D07 and no major outside factor for D04. Whether a real event made the expected outcome less likely came back yes for D06 and D08, no for D04 and uncertain for the other seven.
- The forward look: 45 answers, 32 inferred and 13 unknown. Two signals matched past decisions and carry a suggested action, awaiting a person: an OPEC+ meeting in November 2026 (D08) and EIA's outlook of lower diesel prices in December 2026 (D07 and D09), all three on the Gulf Coast.

### The acceptance tests (E7, 2026-10-29)

E7 turns each of the 21 use cases below into a test, in `pricing_demo/acceptance.py`. Each test asks a concrete form of its question (naming a refinery, a month or a decision, for example) and passes when three things hold: the orchestrator called every agent the row names; the answer holds every figure a SQL check computes from the stores, within half the rounding a reader would use (one decimal for percentages, two for $/bbl and $/gal), each number tied to its own label; and the answer uses a term the row's "Where the ontology matters" column calls for, such as a measure's identifier or label or an evidence label. Use case 1 has no agent: its answer is a walk through the technical graph from the price reference database to the metric views, the measures they implement with their identifiers, the roles `kpi` says use them and the agents that bind them, and its check is Unity Catalog's observed lineage from the price reference replicas. A figure is tied to its label when it sits in the same clause as a word of the label, and, where a word only another figure's label has (the other month, "actual" against "planned") is in that clause too, nearer to a word only its own label has; use case 16's two counts share their words, so each is placed by its role in a phrase such as "4 out of 13". Use case 14 measures each 2026 decision's miss against the bound its expected outcome states, with the actual figure from the hidden decision dossiers in `decision_truth`, which only the tests read; the two widest misses are D08 (about 6.2 times its bound) and D04 (about 3.9 times), far ahead of the next (D06, 0.4). It takes the deciding roles from the decision trail (`graph/decision-trail.ttl`), and looks for a recorded lesson in the stores: a lesson column in the decision log, its evidence or the plan backcast, an evidence item that names one, and the hidden dossiers. It finds none, so it expects the answer to say none is recorded, and fails an answer in which any clause that names a lesson does not hold exactly one negating word (so a claim, or a double negative such as "no lesson was not recorded", fails). The check for use case 10 values the lost throughput as the dossiers do (`decisions.lost_margin`), and gives the same $121.88 million for Robinson and $30.62 million for Anacortes. ### Fixing the failures (Plan 1, after E7)

The plan in the handoff of 2026-10-29 takes the failures above in six steps, each in its own pull request and each measured by a full run, saved in `data/acceptance/` beside the earlier runs and judged again with `rejudge`. `acceptance compare` prints every run's totals and each case's verdict side by side. The checks do not change to make a case pass.

**Step 1, routing** (delegated under EPM-DEC-001-0028). Before calling any agent the orchestrator names the agents whose subject areas the question touches, from their descriptions; a plan that names no known agent is asked again, and after three tries the question stops. Fixed rules add the agents the orchestrator's instructions and the agents' bindings require: a crack figure needs the crack agent; freight and netbacks need the pricing agent, which binds the freight rates; a refinery's runs, utilization, yields or margins, and the plans, backcasts, decisions, events, EIA's weekly data and the outside context, need the refinery agent, which binds those tables. An answer goes back until every planned and required agent has been called. The orchestrator asks at temperature 0. The tests' own lists of required agents are never passed to it, so their agent check still tests the routing. The harness now fails only the case whose check cannot run (run 3's first attempt stopped at use case 14 when the tunnel to `decision_truth` dropped, and kept nothing), and saves the results after every case.

**Step 2, whole rows.** A tool result kept the first 20 rows of an agent's query, and the tool message was then cut at 12,000 characters, which could split a row. A result now keeps up to 500 rows and stays whole JSON under 30,000 characters, dropping rows from the end to fit, and says how many rows the query returned and how many it shows. Run 5 (`2026-10-30-run5.json`, on step 2 over step 1 before its review fixes) passed 4 of 21 (use cases 1, 6, 11 and 21) with 54 agent calls; a required agent was missed in 7 cases, 3 of them on a failed Genie message. **Step 3, retries and three attempts.** A Genie message that fails is sent again, up to three tries ten seconds apart, and each failure stays in the trace; an agent whose every try failed counts as not called, in the orchestrator and in the judge. `acceptance run --repeat 3` asks each case three times, and a case passes only when all three attempts do, as the decision owner asked on 2026-10-30. Run 6 (`2026-10-30-run6.json`, 63 attempts) passed 2 of 21 on all three (use cases 1 and 21). Six Genie messages failed and were retried, none failed after the retry, and no attempt ended on a Genie error, where two to four cases a run had before. A required agent was missed in 6 cases on one attempt or more. A run now records how many attempts it asked for, and a case with fewer recorded, from a run that stopped, is reported as incomplete, not passed. The three attempts show how much the answers vary: use case 17 passed twice in three, use case 3 once, and use cases 6 and 11, which passed on run 5, not at all. Steps 4 to 6 aim at that variation: the agents' SQL and the model.

From the decision owner's enterprise-context-engineering repository on GitHub (its README and `docs/strategy/synthetic-data-generation-strategy.md`, read 2026-10-28), the demo takes the minimal part that use cases 13 to 18 need, and nothing else:

- **Claim-level citations.** Each claim will cite the metric-view query, the evidence item or the ontology IRI behind it.

It leaves out that repository's documents, OT and historian data, storage design, separate fictional company, versioned contracts and evaluation rubric.

## What matches the shared assets, and what does not

- **Matches:** the schema, table, view and column names, except the replica schemas, which follow the source databases' public or generic names since 2026-10-28: the three pricing replicas are `replica_price_assessment`, `replica_price_reference` and `replica_reference_data_hub`, where the shared asset has `replica_mips`, `replica_mpr` and `replica_kittyhawk`, and the three operations replicas (`replica_rightangle`, `replica_aspen_pims`, `replica_production_accounting`) are the demo's own; the crack gold's joins (the MPR settle price unchanged, the MIPS crack sheets, the level-1 group) and constants (`KPI_ID` 'KPI Crack Spread 3-2-1', `Source_System_Id` '17'); the metric views' fields, measures, joins and filters; the benchmark view's defect, all five instruments times 100, and its 160-day window (EPM-DEC-001-0097, Known gaps).
- **Matches, on purpose:** the three crude series the shared system stores two months early (Bakken - Patoka, SYN and WCS; Price Master IDs 30532, 79068, 79069) carry that two-month lag, so the Executive Summary agent's shift rule holds here too.
- **Spelled as the shared asset spells it:** the MPR price master dimension's `Facitlity_Id`, with the shared silver table's misspelling, so a query that names this column runs here unchanged.
- **Differs:** the price detail's high and low prices are left empty, because the demo generates only the settle. The crack view has no `Crack_Spread_Sum`, as the bound view lacks it, so the recreated crack agent says so instead of summing (EPM-DEC-001-0097, Known gaps). The silver fact for MIPS assessments carries `Price_Batch_Id`, so gold takes the effective date from the batch directly. The demo's refinery operations and their metric view are the demo's own; their formulas are not the ontology's definitions, which live in the `kpi` module. Since E3 (2026-10-29) each metric-view measure that implements a `kpi` measure carries its KPI or OPM identifier in its comment, display name and synonyms (the rest say in their comment that they have none), and each view a comment and an `epm_measure_identifiers` tag listing them, which the shared views lack; the measure names are unchanged. The pricing and process-unit metric views and the definitions views are the demo's own.
- **The Genie agents' instructions** are written for this demo from the decision owner's description of the two agents. They are not copies. The two agents E4 added follow the same shape.

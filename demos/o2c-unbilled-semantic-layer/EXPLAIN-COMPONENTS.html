03DuckDB

o2c.duckdb. Warehouse stand-in. No cloud. No Docker. Not Databricks.

What it is

A single-file analytical warehouse at ./o2c.duckdb. MetricFlow has a native DuckDB SQL renderer. The same project pattern (MotherDuck cookbook) could promote to MotherDuck by changing the dbt target. This zip stays local.

What it holds

Everything dbt materializes: seed tables, staging views, intermediate views, marts (fct_unbilled, gold_kpi_unbilled, dim_kpi_metadata, dims, metricflow_time_spine). Regenerated by dbt seed / dbt run.

What it does at runtime

Runs the SQL dbt writes and the SQL MetricFlow compiles. Act 1 and Act 2 Python scripts open this file read-only with the DuckDB Python API. Pin: duckdb==1.5.5.

What it is not

Not Databricks. Not Lakebase. Not Azure. Not Postgres. Not the consumption semantic layer. Not a place that authors Unbilled USD. The unbilled gate is applied in dbt SQL, then stored here.

Where it lives

profiles.yml → path: o2c.duckdb, profile o2c_unbilled, target dev, 4 threads. DBT_PROFILES_DIR=. so dbt does not need ~/.dbt/profiles.yml.

How it connects

In: dbt seed / run. Out: Act 1 / Act 2 scripts and mf query. Nothing in this pack talks to a cloud warehouse.

Failure if you skip it

There is no Track A. Do not stand up Postgres or Databricks “to get a real warehouse” for this lesson. DuckDB is the warehouse on purpose: one file, no account, no network.

Not the programme warehouse

Programme consumption semantic layer is Databricks Metric Views (Demo 2 / Track B). This file warehouse is the demo-1 stand-in only. Do not blur them.

04dbt Core

Builds tables. Hosts YAML. Free. Why 1.10, not 1.12.

What it is

dbt Core on the 1.10 line. Two jobs in this demo: (1) build tables from CSV seeds, (2) host the YAML MetricFlow compiles. Free. No dbt Cloud. No paid account.

What it holds

Project o2c_unbilled. require-dbt-version: [>=1.10.0, <1.11.0]. Var as_of_date: "2026-08-01". Staging views, intermediate views, marts as tables. Legacy standalone YAML in models/semantic_models.yml.

What it does at runtime

dbt seed loads 7 CSVs (PASS=7). dbt run builds 19 models (11 tables + 8 views). dbt parse writes target/semantic_manifest.json. mf reads that manifest plus the materialized DuckDB tables. dbt test on the three certified objects: PASS=13.

What it is not

Not the compiler (MetricFlow is). Not a KPI Store. Not dbt 1.12. Not a place that parses osi/ — dbt Core only parses osi/ on 1.12+. This project stays on 1.10 so mf --explain keeps working with MetricFlow 0.11.

Where it lives

dbt_project.yml, profiles.yml, models/, tests/, analyses/act1_conflicting_reports.sql. Pins: dbt-core==1.10.23, dbt-duckdb==1.10.1, dbt-metricflow==0.11.0.

How it connects

In: seeds + SQL models. Out: DuckDB tables and the semantic manifest. MetricFlow is a separate CLI (mf) that consumes the manifest.

Failure if you skip it

No tables, no YAML host, no manifest. Do not replace dbt with hand-written CREATE TABLE in this pack — the lesson is “one certified fact, then a compiler.” Do not upgrade to 1.12 to “use Ossie.” That breaks the 0.11 compiler pin.

Why the 1.10 line

The originally requested pins (dbt-core>=1.8,<1.10 and dbt-metricflow>=0.10) cannot resolve. Published dbt-metricflow 0.10.x / 0.11.0 require dbt-core>=1.10.4,<1.11.0. We relaxed only the dbt-core / dbt-duckdb upper bound to the 1.10 line so the legacy standalone YAML spec still applies. dbt 1.12’s embedded semantic_model: under models: is avoided on purpose.

dbt 1.10 warns that semantic-models.time-spine in dbt_project.yml is an unused path. The working time-spine config is models/metricflow_time_spine.yml (model-level time_spine:) plus time_spines: in semantic_models.yml. The project-level block is kept because the MotherDuck 1.8/1.9 cookbook uses it. Ignore the deprecation banner. Ignore any CLI nag to upgrade MetricFlow to 0.13.0 — 0.13 is a different line.

Typed views. No business rule. The first dbt layer.

What it is

Seven views in schema staging, materialized as views: stg_deliveries, stg_invoice_lines, stg_invoices, stg_parties, stg_party_roles, stg_products, stg_terminals.

What it holds

The same rows as the seeds, with casts. stg_deliveries derives delivery_date from bol_ts and lowercases status. stg_invoices lowercases invoice_status and casts dates and amounts.

What it does at runtime

Sits still. int_ticket_billing and the dims read these views. No unbilled test here. No multiply here.

What it is not

Where it lives

How it connects

In: seed tables. Out: intermediate billing status and the mart dims / facts.

Failure if you skip it

07int_ticket_billing

is_unbilled / is_billed. Quality-hold is false on both. The gate starts here.

What it is

Ticket-level billing status as of var('as_of_date') (2026-08-01). An invoice line counts only when the parent invoice_date <= as_of and invoice_status = 'posted'.

What it holds

Every delivery, plus optional invoice fields, plus two flags. is_billed is true only when status is not quality_hold and a qualifying invoice line exists. is_unbilled is true only when status is delivered and no qualifying invoice line exists.

What it does at runtime

Left-joins posted-as-of lines onto deliveries. Quality-hold tickets get is_billed = false and is_unbilled = false. They are not billable until released. They are never billed and never unbilled.

What it is not

Not the published fact. Not gold. Not a dollar formula — prices join later on fct_delivery. Not a customer grain.

Where it lives

models/intermediate/int_ticket_billing.sql. Materialized as a view in schema intermediate.

How it connects

In: stg_deliveries, stg_invoice_lines, stg_invoices. Out: fct_delivery (names + prices + both flags) then fct_unbilled (filter is_unbilled).

Failure if you skip it

You will encode the gate twice, or forget quality-hold, or treat a draft / post-as-of invoice as billed. The certified rule lives in this join plus the fct_unbilled filter.

The two flags, in English

is_billed = not quality-hold AND a posted invoice line dated on or before 2026-08-01. is_unbilled = delivered AND no such line. Quality-hold is the third state: neither.

08fct_unbilled

Ticket grain. Certified population + formula. Compiler source. Not gold.

What it is

One row per unbilled BOL ticket. The certified rule as of 2026-08-01: status = delivered, no posted invoice line with invoice_date <= 2026-08-01, unbilled_usd = gallons_net * contract_price_usd, quality-hold never billed and never unbilled.

What it holds

446 ticket rows. Sold-to, payer, bill-to, terminal, product, net and gross gallons, both prices, unbilled_usd (aliased from fct_delivery.contract_value_usd), as_of_date. Easy to audit back to a BOL.

What it does at runtime

select … from fct_delivery where is_unbilled and status = 'delivered'. The multiply already happened on fct_delivery as round(gallons_net * contract_price_usd, 2). This model seals the population.

What it is not

Not gold. Not a layer named Certified. Not a catalog. Not a customer grain choice. Not the compiler. Delete the YAML and this table still answers Act 1.

Where it lives

models/marts/fct_unbilled.sql. Tests: unique/not-null ticket_id, not-null dollars and keys. Custom test assert_unbilled_excludes_holds.sql.

How it connects

In: fct_delivery (which joined int_ticket_billing to parties, terminals, products). Out: Act 1 A/B, gold, MetricFlow semantic model unbilled_tickets.

Failure if you skip it

There is no certified ticket set. Do not let MetricFlow SUM staging. Do not put the multiply in YAML. Do not treat gold as the population.

Proven population

446 tickets. $6,049,649.77 as of 2026-08-01. Seed=42. That is the number Act 1 A/B and mf query --metrics unbilled_usd --decimals 2 must both hit.

09dim_kpi_metadata

One row. Grain lives on the fact. Not a KPI Store catalog.

What it is

One certified KPI row. kpi_id = KPI-O2C-UNBILLED-USD. formula_pointer = unbilled_usd (the MetricFlow metric name). Status = certified. Owner = Revenue Accounting / Order-to-Cash. Default grain rule as English: sold_to + terminal + day.

What it holds

Name, owner, a prose definition, UOM = USD, the pointer, as-of date. That is all. One row. Tests require unique kpi_id, accepted formula_pointer = unbilled_usd, accepted status = certified, and a custom test that the table has exactly one row.

What it does at runtime

Where it lives

How it connects

Failure if you skip it

The number still compiles. Learners will treat gold or YAML as “the catalog.” Keep the one-row stub so C-10 stays visible: pointer ≠ formula.

11semantic_models.yml

Legacy standalone spec. Entities, dims, measures, metrics. Time spine. Compile SoT.

What it is

The compile source of truth for MetricFlow. Top-level time_spines:, semantic_models:, metrics:. Not the dbt 1.12 embedded semantic_model: block under models:. Written for the 1.8–1.11 line.

What it holds

Semantic model unbilled_tickets on ref('fct_unbilled'). Primary entity ticket (ticket_id). Foreign entities sold_to_party, payer_party, terminal_loc, product_sku. Time delivery_date (day) as default agg_time_dimension. Categorical dimensions sold_to, payer, terminal, product, status — names distinct from entity names so they do not collide. Measures unbilled_usd_measure (sum of column unbilled_usd), unbilled_gallons_net_measure, ticket_count. Metrics unbilled_usd, unbilled_gallons_net, unbilled_ticket_count.

What it does at runtime

dbt parse writes it into target/semantic_manifest.json. MetricFlow reads the manifest and compiles SUM(unbilled_usd) FROM fct_unbilled. It does not re-encode the unbilled rule.

What it is not

Not the formula source of truth (the fact is). Not Ossie. Not ontology. Not dbt 1.12. Do not rewrite it as embedded blocks. Do not point mf at osi/unbilled.ossie.yaml.

Where it lives

models/semantic_models.yml. Time spine also declared in models/metricflow_time_spine.sql (2026-01-01 … 2026-08-31) and metricflow_time_spine.yml (what dbt 1.10 actually reads).

How it connects

In: the fact’s column names. Out: the manifest → mf query. Group-by CLI names become ticket__sold_to etc. because MetricFlow 0.209 prefixes categorical dimensions with the primary entity.

Failure if you skip it

Act 1 still works. Act 3 does not. The lesson “one certified formula, one compile path” needs this file. Do not replace it with a hand-written second SQL that happens to match.

ticket__ is compiler namespacing

It is not a claim that sold-to is a child of ticket. mf list dimensions --metrics unbilled_usd shows the names you may group by. Bare sold_to is not a group-by item.

12MetricFlow compiler

mf query / --explain. ticket__ prefix. 0.11 pin. Do not upgrade to 0.13.

What it is

The demo-1 compiler. dbt-metricflow==0.11.0 wrapping metricflow==0.209.0. CLI is mf. Consumption semantic layer (MetricFlow on DuckDB) for this pack only. Programme consumption semantic layer is Databricks Metric Views (Demo 2 / Track B).

What it holds

No durable data of its own. It reads target/semantic_manifest.json and the materialized DuckDB tables. It writes SQL.

What it does at runtime

mf list metrics finds 3 metrics. mf query --metrics unbilled_usd --explain prints SELECT SUM(unbilled_usd) AS unbilled_usd FROM "o2c"."main"."fct_unbilled". Unsliced query with --decimals 2 returns 6049649.77. Group-by sold-to or payer changes only the GROUP BY list.

What it is not

Not Databricks Metric Views. Not Cube. Not a KPI Store. Not ontology. Not MetricFlow 0.13. The CLI may nag that 0.13.0 is available. Do not upgrade — 0.13 wants dbt-core 1.10.4–1.12 and is a different line. YAML/pins break.

Where it lives

Installed into the venv from requirements.txt. which mf must be .venv/bin/mf. On a Mac, bare mf can resolve to TeX Metafont — call .venv/bin/mf explicitly.

How it connects

In: manifest + fct_unbilled + time spine. Out: compiled SQL against DuckDB. RC-1: this is the one compile path.

Failure if you skip it

You still have a certified fact and two honest reports. You lose the “compiler writes the SELECT” lesson. Do not skip by writing a second SQL that matches. Do not swap in Cube or a Metric View.

Python 3.13 will not resolve dbt-metricflow 0.11

Use Python 3.11 or 3.12 only. The verification box used 3.12.13 via uv because system Python was 3.13.5.

15Ossie projection

What it is

A portable Apache Ossie (formerly OSI) projection of the certified metric, spec 0.1.1, at osi/unbilled.ossie.yaml. Interchange. Another tool could read the metric name, grain, and expression. Nothing in this zip does.

What it holds

Semantic model o2c_unbilled, dataset fct_unbilled, the same expression described as SUM of the fact column. ai_context says: unbilled is a state of an obligation; do not group by a generic “customer”; ship-to is a terminal; do not treat this YAML as OWL. relationships are join paths for a semantic model, not OWL object properties.

What it does at runtime

Nothing. dbt 1.10 does not parse osi/. mf is not pointed at this file. Live main Ossie schema is 0.2.0.dev0 and would fail validation against this 0.1.1 file. Park that.

17Quiz

Ten short questions. One idea each, in lesson order. Answers are collapsed. Ask Hamid to answer out loud before opening them.

Q1 · is this a KPI Store?

Is this pack a KPI Store catalog? What is dim_kpi_metadata?

Answer
No. This demo is the consumption semantic layer (MetricFlow on DuckDB). dim_kpi_metadata is one stub row. formula_pointer = unbilled_usd. A Store would certify definition / owner / status. Do not grow the stub into a catalog here.
Q2 · why A and B match but fight

Report A and Report B both total $6,049,649.77. Why do they still fight?

Answer
Same 446 tickets, different group-by. A has 4 sold-to rows. B has 3 payer rows. Apex Fuels LLC ($4,095,877.44 / 296) equals Houston Rack + Dallas Dealer. Adding those three “customer” lines double-counts. Aviation matches because GCA is both roles. The fight is grain, not a data-quality bug.
Q3 · what does --explain prove

What does mf query --metrics unbilled_usd --explain prove, and why is the SQL so short?

Answer
It proves the compiler: YAML → SQL. The SQL is SUM(unbilled_usd) FROM fct_unbilled on purpose. The unbilled rule is already sealed on the fact. MetricFlow does not re-encode gallons_net * contract_price. A long CASE in the compiled SQL would be a fail.
Q4 · why not upgrade dbt

Why stay on dbt 1.10 / MetricFlow 0.11? Why not upgrade to dbt 1.12 to “use Ossie,” or to MetricFlow 0.13?

Answer
dbt 1.12 parses osi/ and wants embedded semantic_model: blocks. This YAML is the legacy standalone spec. MetricFlow 0.11 needs dbt-core ≥1.10.4,<1.11. 0.13 is a different line and breaks this pin set. Nobody in this demo reads the Ossie file. Upgrading to “use Ossie” breaks the compiler that is the lesson.
Q5 · ticket__ prefix

Why is the group-by ticket__sold_to and not sold_to? Does that mean sold-to is a child of ticket?

Answer
MetricFlow 0.209 prefixes categorical dimensions with the primary entity (ticket). That is compiler namespacing, not a claim that sold-to is a child of ticket. Bare sold_to is not a group-by item. Use mf list dimensions --metrics unbilled_usd.
Q6 · Ossie vs compile YAML

What is models/semantic_models.yml, and what is osi/unbilled.ossie.yaml?

Answer
The first is the compile SoT: legacy standalone spec that MetricFlow compiles. The second is a portable Ossie projection. Nobody in this demo reads it. Neither file is the formula source of truth — that is fct_unbilled. Ossie relationships are join paths, not OWL. This zip has no ontology.
Q7 · C-10 / C-11

What does C-10 split? What must you always say instead of “the semantic layer”?

Answer
C-10: meaning vs formula. Fact = population + formula. YAML = name + SUM column. Metadata points. Ossie is interchange, not meaning-as-OWL. C-11: always say consumption semantic layer (MetricFlow on DuckDB). Never bare “the semantic layer.” Programme consumption semantic layer is Databricks Metric Views (Demo 2).
Q8 · Report C

Why is Report C $7,393,499.19, and what does the consumption semantic layer do about it?

Answer
Gross gallons × list price, includes quality-hold, mixes sold-to and payer labels. Different basis, not a different group-by of the certified set. The consumption semantic layer replaces C; it does not average A/B/C. Act 3 matches A/B. C stays different because it never used the fact / the metric.
Q9 · gold vs fact

What is fct_unbilled, and what is gold_kpi_unbilled?

Answer
fct_unbilled is the population + formula at ticket grain (446 rows). gold_kpi_unbilled is a published snapshot SELECT from that fact at sold-to + terminal + day (195 rows). Not a second formula. Metadata stays 1 row. Grain lives on the fact.
Q10 · do not mix packs

What compiler and warehouse is this pack? What must you not open while teaching it?

Answer
Compiler is MetricFlow 0.11 / 0.209 over DuckDB. Not Databricks, not Metric Views, not Lakebase, not Genie, not Azure. Do not run Track B scripts. Do not treat MetricFlow as the programme consumption semantic layer — that seat is Demo 2 Metric Views. MetricFlow is the demo-1 compiler only.

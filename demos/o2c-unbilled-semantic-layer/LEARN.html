01 What you are building (the picture)

Story + certified rule + A/B/C. One population. One compiler. No ontology in this zip.

Why. You need the story in your head before you write a line of SQL. Two workbooks both titled Unbilled USD fight on grain. A third fights on basis. You will replace them with one certified fact and one MetricFlow metric.

A Gulf Coast fuels marketer lifts product at three terminals (Houston Ship Channel, Dallas, Beaumont). Invoices go to the payer, not the sold-to.

  • Apex Fuels LLC is the payer for two sold-tos: Houston Rack and Dallas Dealer.
  • Gulf Coast Aviation Inc is payer and sold-to (same org).
  • Metro Lubricants pays for Metro Lubes Beaumont.
  • Ship-to is a terminal, not a customer role. HSC / DAL / BMT.

Certified rule as of 2026-08-01:

  • status = delivered
  • no posted invoice line with invoice_date <= 2026-08-01
  • unbilled_usd = gallons_net * contract_price_usd
  • quality-hold never billed and never unbilled

02 Python 3.12 + uv venv

3.13 will fail. Pins are locked. Homebrew is not required. Docker is not required.

Why. dbt-metricflow==0.11.0 requires Python <3.13 and dbt-core>=1.10.4,<1.11. The verification box used 3.12.13 via uv because system Python was 3.13.5. If you start on 3.13 you will spend an hour on a resolver error that is not the lesson.

  1. Check: python3 --version. You need 3.11 or 3.12. If you only have 3.13, install 3.12 from python.org and pass --python 3.12 to uv venv.
  2. Install uv if needed: docs.astral.sh/uv.
  3. From your scratch folder (create it in §3 first, or create the venv after the skeleton): 
    # Python 3.11 or 3.12 only (3.13 will not resolve dbt-metricflow 0.11)
uv venv --python 3.12
source .venv/bin/activate
uv pip install -r requirements.txt
  4. Confirm: 
    dbt --version
# Core: 1.10.23   Plugin duckdb: 1.10.1
which mf
# …/.venv/bin/mf
python -c "import duckdb, metricflow; print(duckdb.__version__)"
# 1.5.5

Without uv (fallback):

python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
pip install -r requirements.txt

requirements.txt you write (these exact pins):

dbt-core==1.10.23
dbt-duckdb==1.10.1
dbt-metricflow==0.11.0

Resolved on the verification box: metricflow==0.209.0, duckdb==1.5.5. Do not add Cube, Airflow, or a Databricks SDK.

Done when

Venv is 3.11 or 3.12. dbt --version shows 1.10.23 / duckdb 1.10.1. which mf is .venv/bin/mf. No 0.13 install.

Pitfall — Python 3.13 / No matching distribution for dbt-metricflow

Use 3.11 or 3.12. 0.10/0.11 require <3.13. Do not “just pip install the latest MetricFlow.” 0.13 is a different line and will break the legacy YAML.

Pitfall — mf not found, or mf opens Metafont

source .venv/bin/activate. which mf must be .venv/bin/mf. On a Mac, bare mf can resolve to a TeX Metafont binary. Call .venv/bin/mf explicitly. python -m dbt.cli.main is not the MetricFlow CLI.

06 int_ticket_billing + fct_unbilled

The certified rule. Population + formula. Not gold. Not YAML.

Why. This is the formula source of truth. YAML will only name the metric and the SUM column. If the gate or the multiply leaks into YAML, Act 3 --explain will not be a short SUM(unbilled_usd) FROM fct_unbilled.

int_ticket_billing

Write models/intermediate/int_ticket_billing.sql. Ticket-level billing status as of var('as_of_date').

  1. CTE of invoice lines joined to invoices where invoice_date <= as_of and invoice_status = 'posted'.
  2. From stg_deliveries, left join that CTE on ticket_id.
  3. is_billed = false when status is quality_hold; else true when a line exists.
  4. is_unbilled = true only when status is delivered and no line exists.

Quality-hold is never billed and never unbilled. That is the third state. Do not invent a fourth flag.

fct_delivery (names + prices)

Write models/marts/fct_delivery.sql. This is the wide delivery fact — billed, unbilled, and quality-hold all still present. Join int_ticket_billing to:

  • stg_parties three times (sold-to, payer, bill-to) so names sit on the row.
  • stg_terminals for terminal_name.
  • stg_products for product_name, contract_price_usd, list_price_usd.

Compute round(gallons_net * contract_price_usd, 2) as contract_value_usd and, if you want Report C later, round(gallons_gross * list_price_usd, 2) as sloppy_value_usd. Keep both flags. Contract ≠ list on every product (RBOB 2.184 / 2.269, ULSD 2.312 / 2.407, Jet-A 2.156 / 2.248). That gap is why C drifts even before quality-hold.

Do not filter to unbilled here. fct_unbilled is the filter. Report C needs the wider set.

fct_unbilled

Write models/marts/fct_unbilled.sql:

select
    ticket_id, …,  -- keys, names, gallons, prices, status
    contract_value_usd as unbilled_usd,
    date '{{ var("as_of_date") }}' as as_of_date
from {{ ref('fct_delivery') }}
where is_unbilled
  and status = 'delivered'

Grain: one row per BOL. Default published grain (gold, next section) is sold-to + terminal + day. Product is a slice, not part of that grain.

Done when

After §10: fct_unbilled has 446 rows. select round(sum(unbilled_usd), 2) from fct_unbilled is 6049649.77. Zero quality_hold rows. A custom test assert_unbilled_excludes_holds should pass.

Pitfall

Filtering on invoice presence without the as-of date and posted status will drop tickets whose invoice is after 2026-08-01 (they are still unbilled). Peek if stuck: complete pack models/intermediate/int_ticket_billing.sql and models/marts/fct_unbilled.sql. Write the filter yourself. Do not put the multiply in YAML.

08 Time spine

2026-01-01 … 2026-08-31. MetricFlow needs a day spine. Lifts are Jun–Jul 2026.

Why. MetricFlow joins measures to a time spine for metric_time slices. Empty metric_time results usually mean the spine does not cover the lift dates, or dbt 1.10 did not see the model-level config.

Write models/metricflow_time_spine.sql:

{{ config(materialized='table') }}
select cast(date_day as date) as date_day
from (
    select unnest(generate_series(
        date '2026-01-01',
        date '2026-08-31',
        interval '1 day'
    )) as date_day
) dates

Write models/metricflow_time_spine.yml — this is what dbt 1.10 actually reads:

version: 2
models:
  - name: metricflow_time_spine
    time_spine:
      standard_granularity_column: date_day
    columns:
      - name: date_day
        granularity: day

Also declare time_spines: at the top of semantic_models.yml in §9. The project-level semantic-models.time-spine block in dbt_project.yml is the 1.8/1.9 cookbook pattern; dbt 1.10 warns it is unused. You may keep it. Do not rely on it alone.

Done when

After §10: the spine table has one row per day 2026-01-01 through 2026-08-31. Later, mf query … --group-by metric_time__day returns Jun–Jul 2026 rows, not an empty frame.

Pitfall — empty metric_time

Spine must cover the lifts. Re-run dbt run after adding the YAML. Peek: models/metricflow_time_spine.sql and models/metricflow_time_spine.yml.

09 semantic_models.yml

Legacy standalone spec. Do not write dbt 1.12 embedded blocks.

Why. This file is the compile SoT. It names the metric and which column to SUM. It does not re-encode the unbilled rule. If you write dbt 1.12 semantic_model: under models:, you have left the pin set this demo compiles with.

Write models/semantic_models.yml with three top-level keys: time_spines:, semantic_models:, metrics:.

  • Time spine: name time_spine, model ref('metricflow_time_spine'), column date_day, grain day.
  • Semantic model unbilled_tickets on ref('fct_unbilled'). Default agg_time_dimension: delivery_date.
  • Primary entity ticket / ticket_id. Foreign entities sold_to_party, payer_party, terminal_loc, product_sku (use ids / codes, and names that do not collide with dimension names).
  • Time dimension delivery_date (day). Categorical dimensions sold_to (expr sold_to_name), payer, terminal, product, status.
  • Measures: unbilled_usd_measure agg sum expr unbilled_usd; unbilled_gallons_net_measure sum of gallons_net; ticket_count count of ticket_id.
  • Metrics (type simple): unbilled_usd, unbilled_gallons_net, unbilled_ticket_count, each pointing at the matching measure.
What you are not writing

You are not writing gallons_net * contract_price again. You are not writing dbt 1.12 embedded blocks. You are not pointing MetricFlow at osi/unbilled.ossie.yaml. You are not authoring ontology IRIs.

Done when

After §10’s dbt parse: target/semantic_manifest.json exists. mf list metrics (in §13) finds the three metrics. Do not run mf yet if the fact is not built.

Pitfall

Dimension names must be distinct from entity names or MetricFlow will collide. That is why the entities are sold_to_party and the dimension is sold_to. Peek if stuck: complete pack models/semantic_models.yml. Copy structure, not a 1.12 rewrite.

10 dbt seed / run / parse / test

Materialize the warehouse. Write the manifest. Then, and only then, Act 1.

11 Act 1 — write the three reports

Or run act1_reports.py after you understand them. A and B share tickets. C does not.

Why. Two honest “customer” reports fight on grain. The sloppy twin fights on basis. You must see that before the compiler is interesting. Act 1 A/B already query the fact. Act 3 will be the same number through mf query.

Write three queries against o2c.duckdb (Python + duckdb, or the dbt analysis analyses/act1_conflicting_reports.sql, or a SQL client).

Report A — sold-to, certified ticket set

select sold_to_name as customer,
       round(sum(unbilled_usd), 2) as unbilled_usd,
       count(*) as tickets
from fct_unbilled
group by 1

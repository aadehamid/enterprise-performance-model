01 What you are building (the picture)

One Unbilled population. Three certified Metric Views. Gold publishes all three FROM MEASURE(). Genie is the ad hoc path for all three (after KPI 2/3). Meaning lives beside them, not inside them.

Unbilled is a state of an Obligation (a delivered BOL not yet invoiced). It is not a KPI kind. You choose the group-by. The formula stays still. customer_grain ∈ {payer, sold-to, site}.

ODS
Lakebase dataexpert-day1 / databricks_postgres / o2c_unbilled Existing project only. Schema o2c_unbilled only. Seven ops tables. Optional (you can skip to CSV).
Bronze
raw_* replica Python pipe from Lakebase, or CSV upload. No federated join from the warehouse. Same seven tables: parties, party_roles, products, terminals, tickets, invoices, invoice_lines.
Silver
dims + dim_kpi_metadata Thin dims (party, site, product, role bridge). Metadata is one row per KPI (all certified) and a pointer only. It does not author the formula.
Population
fct_unbilled Ticket grain. Compiler source. Not gold. The ticket gate and gallons_net * contract_price live here. Honest seats.
Compiler
Metric View unbilled_usd YAML inside the view. Version 0.1 (fields + measures). Compiles SUM / GROUP BY. KPI 2/3 are extra views (bronze star, multiply in YAML, no population fact). Gold uses MEASURE() per KPI. Genie asks all three views after KPI 2/3.
Gold
gold_kpi_value FROM MEASURE() Published instances per certified KPI FROM that view’s MEASURE(). Unbilled grains: enterprise / payer / sold_to / site. Not a second SUM() of the fact.
Ad hoc
Genie Agent - O2C certified KPIs / three views One agent, three views, after KPI 2/3. Grain questions in English. Export-to-metric-view is forbidden (that would mint a second formula).

Honest seats

The ticket gate (delivered, no posted invoice as of the as-of date, quality-hold excluded) and the dollars (gallons_net * contract_price) live on fct_unbilled. The Metric View is SUM and GROUP BY over that sealed column. Gold publishes each certified KPI FROM that view’s MEASURE() (RC-1 per KPI). Genie is the ad hoc path for all three (after KPI 2/3). If either re-encodes the product, the exercise failed even when the dollars match.

Proven proof (not a target)

12 tickets. $179,934.00 as of 2026-08-01. That number was computed from the seed CSVs and compiled live on Free with Metric View version 0.1. You are rebuilding until you hit the same proof. You are not inventing a new total.

C-10 in one line

Ontology = meaning. Population (fct_unbilled) holds the ticket gate + gallons_net * contract_price. The Metric View compiles SUM / GROUP BY. Gold and Genie use MEASURE() and must not re-encode. They agree. They are not one object. Do not pretend the Metric View is the ontology or the only formula SoT.

06 fct_unbilled

Seal the certified population at ticket grain. This is not gold. This is not a second published formula.

Why. A consumption semantic layer compiles a measure. It should not re-decide who is unbilled. You seal the ticket set first. Delete the Metric View later and Act 1 still works. That is the production pattern.

The rule (as of 2026-08-01)

A ticket is unbilled when all of these are true:

  1. status = 'delivered'.
  2. No posted invoice line whose invoice has invoice_date <= DATE '2026-08-01'.
  3. Quality-hold is never billed and never unbilled. Those tickets are not delivered, so the status filter drops them. Do not special-case them into the unbilled set.
  4. unbilled_usd = gallons_net * contract_price (contract price from the product, not list price). Cast to a money type you can sum cleanly (two decimal places).

What you write (the shape, not the answer file)

Fill this pack’s sql/02_facts.sql. Two parts.

Part 1. Thin dims. Star-ish copies so names are easy to join:

  • dim_party from raw_parties.
  • br_party_role from raw_party_roles (payer / sold_to / bill_to). GCA holds all three.
  • dim_site from raw_terminals (terminal_code → site_code, terminal_name → site_name).
  • dim_product from raw_products (keep contract_price_usd and list_price_usd so you can see they differ).

Part 2. The fact. One row per BOL ticket that passes the rule. Suggested build:

  1. A CTE (call it posted_as_of) that lists ticket_id from raw_invoice_lines joined to raw_invoices where invoice_status = 'posted' and invoice_date <= DATE '2026-08-01'.
  2. From raw_tickets, keep status = 'delivered' and anti-join that CTE (left join, keep rows where the posted ticket id is null).
  3. Join products for contract price. Join parties three times (sold-to, payer, bill-to) so names sit on the fact. Join dim_site for site_name.
  4. Denormalize those names onto the fact. The Metric View stays one source table. It does not join.
  5. Stamp as_of_date = DATE '2026-08-01' on every row. Compute delivery_date from the BOL timestamp.

Two invoice rows exist so the as-of rule is visible. INV-2026-0005 is posted on 2026-08-03 against BOL-2026-0104. After as-of, so that ticket stays unbilled. INV-2026-0006 is draft and does not count. If your fact drops 0104, your as-of test is wrong.

Then run a check. Expect 12 tickets and $179,934.00:

SELECT
  COUNT(*)          AS unbilled_tickets,
  SUM(unbilled_usd) AS unbilled_usd
FROM {{catalog}}.{{schema}}.fct_unbilled;
Done when

07 Metric View version 0.1

Author the YAML yourself. Compile it. Version 0.1 is the live-proven dialect. Fields + measures. Nothing else.

Why. This is the compiler. Gold and Genie will both ask it. If you export a view from Genie, or author YAML 1.1 agent metadata, you will spend the afternoon debugging indent and keys that Free never compiled as the pack dialect.

Write 0.1 (the live-proven pack dialect)

Complete pack sql/03_metric_view.sql is the live-proven version 0.1 (same YAML as scripts/04_metric_view.py). Fields + measures only. Peek that file if stuck. Do not author YAML 1.1 comment / display_name / synonyms - that is not the pack dialect.

Do not Export from Genie. You author this.

The dialect (teaching the shape)

One statement. CREATE VIEW … WITH METRICS LANGUAGE YAML. The YAML lives inside a $$ … $$ block. Source is fct_unbilled. You choose the group-by later. The formula stays still. Official: Create a metric view.

Write this into this pack’s sql/03_metric_view.sql. Replace the placeholders with your catalog and schema. Paste it as one block.

CREATE OR REPLACE VIEW {{catalog}}.{{schema}}.unbilled_usd
WITH METRICS
LANGUAGE YAML
AS $$
version: 0.1
source: {{catalog}}.{{schema}}.fct_unbilled
fields:
  - name: payer
    expr: source.payer_name
  - name: sold_to
    expr: source.sold_to_name
  - name: site
    expr: source.site_code
  - name: site_name
    expr: source.site_name
  - name: as_of
    expr: source.as_of_date
  - name: delivery_date
    expr: source.delivery_date
  - name: product
    expr: source.product_code
measures:
  - name: unbilled_usd
    expr: SUM(source.unbilled_usd)
  - name: unbilled_ticket_count
    expr: COUNT(1)
$$

That is the whole 0.1 surface: seven fields, two measures. No time spine. No MetricFlow entity prefix (ticket__sold_to). Group by the field names as written. The measure unbilled_usd is SUM of the column you already sealed. It does not multiply gallons again.

After it creates, prove the compiler:

SELECT MEASURE(unbilled_usd) AS unbilled_usd
FROM {{catalog}}.{{schema}}.unbilled_usd;

Expect $179,934.00.

Done when

The view creates as one statement. MEASURE(unbilled_usd) returns a number. You wrote the YAML. You did not export it from Genie. You wrote version 0.1 (fields + measures), not YAML 1.1 agent metadata.

Pitfall. Monaco auto-indent mangles YAML

The SQL Editor will “helpfully” indent when you paste line by line. YAML cares. Paste the whole CREATE … AS $$ … $$ as one block. Then visually check that fields: / measures: are at the same indent, and that each - name: lines up. If create fails with a YAML parse error, it is almost always indent. Also: SELECT * against this view is refused later (Act 3). Do not debug 0.1 by starring the view.

08 Act 1. Conflicting customer reports on the fact

Two honest group-bys, both labeled “customer,” fight at the row level. Same tickets. Same total. Different rows.

Why. Downstream O2C overloads the word “customer.” Credit lives on the payer. Dealer performance lives on the sold-to. Site is a terminal, not a party. If you default the KPI to one of those, the other report looks like a data-quality bug. It is not. It is grain.

Query fct_unbilled. Not the Metric View yet. Write both reports in this pack’s sql/04_queries.sql.

  • Report A. Group by sold-to. Alias the name as customer.
  • Report B. Group by payer. Alias the name as customer.

Select the name, SUM(unbilled_usd), and a ticket count. Do not paste a second gallons_net * contract_price into the query file. The ticket gate and the product already live on the fact (the population). The Metric View compiles SUM / GROUP BY. Act 1 is a group-by lesson, not a second compiler.

09 Act 2. MEASURE() at payer / sold_to / site

Same ticket set. Same total. Three grains. Through the compiler, not a second SQL copy of the formula.

Why. Act 1 proved the grain fight on the fact. Act 2 proves the compiler gives the same numbers without you writing SUM at query time. That is the whole point of a consumption semantic layer.

In the same sql/04_queries.sql, add three queries against the Metric View. You do not write SUM for that measure. You do not re-encode gallons_net * contract_price.

SELECT MEASURE(unbilled_usd) AS unbilled_usd
FROM {{catalog}}.{{schema}}.unbilled_usd;

SELECT payer, MEASURE(unbilled_usd) AS unbilled_usd,
       MEASURE(unbilled_ticket_count) AS tickets
FROM {{catalog}}.{{schema}}.unbilled_usd
GROUP BY payer;

SELECT sold_to, MEASURE(unbilled_usd) AS unbilled_usd,
       MEASURE(unbilled_ticket_count) AS tickets
FROM {{catalog}}.{{schema}}.unbilled_usd
GROUP BY sold_to;

SELECT site, site_name, MEASURE(unbilled_usd) AS unbilled_usd,
       MEASURE(unbilled_ticket_count) AS tickets
FROM {{catalog}}.{{schema}}.unbilled_usd
GROUP BY site, site_name;

MEASURE() inherits the aggregation from the YAML. Official query page: Query metric views. Every measure uses MEASURE().

10 Act 3. SELECT * must fail

See Databricks refuse a metric view treated as a regular table. Then go back to MEASURE().

Why. The refusal is how the platform stops a consumer from starring a metric view and accidentally re-aggregating a measure. You want to see the error once, write it down, and never debug around it.

Run this on purpose:

It should error. Expect something like METRIC_VIEW_MISSING_MEASURE_FUNCTION. Write the exact message in a comment in sql/04_queries.sql (keep the SELECT * commented after you have seen it). Then go back to MEASURE(unbilled_usd).

Done when

The statement errors. You wrote the message down (expect METRIC_VIEW_MISSING_MEASURE_FUNCTION). You went back to MEASURE(unbilled_usd).

Pitfall

Do not “fix” the view so SELECT * works. The refusal is the feature. Peek if stuck: complete pack sql/04_queries.sql (Act 3, the commented SELECT *) and WALKTHROUGH.md §7.

11 Store. One row per KPI, gold FROM MEASURE()

dim_kpi_metadata points at each view. gold_kpi_value snapshots FROM MEASURE() per certified KPI. Replace-by-kpi_id. Metadata does not author the formula.

Why. The Store certifies definition, owner, status, and grain rule, and it publishes instances. It does not grow a second Unbilled formula. RC-1 per KPI: one compile path each. After this step the Unbilled row exists. After §12–§13 the catalog is three certified rows and Gold has all three KPIs. Genie (§14) then attaches all three views.

Write this pack’s sql/05_store.sql. Two objects. Do not paste the complete-pack file. Teach yourself the pointer, then replace-by-kpi_id gold. Do not wipe the table.

Silver: dim_kpi_metadata (one row per KPI)

After this store step, upsert the Unbilled row. Pointer, not a SQL formula. Suggested columns:

  • kpi_id = KPI-O2C-UNBILLED-USD.
  • name, owner, definition, uom (USD), status (certified).
  • allowed_grain = enterprise, payer, sold_to, site. default_grain_rule = enterprise | payer | sold_to | site. Metadata does not restate the formula.
  • gating_rule in English (delivered, no posted invoice as of as-of, quality-hold excluded). Not a second SQL body.
  • formula_pointer = the measure name unbilled_usd. Not gallons_net * contract_price.
  • formula_object = {{catalog}}.{{schema}}.unbilled_usd.
  • formula_version = 0.1.
  • ontology_iri = #UnbilledState (the pack uses https://example.org/domain-ontology-kpi/o2c#UnbilledState).
  • as_of_date = 2026-08-01.

Create the table if missing, then upsert only the Unbilled row. Do not CREATE OR REPLACE the catalog table (that wipes KPI 2/3 if they already exist). After §12–§13 expect 3 certified rows. Join gold to this table on kpi_id.

Gold: gold_kpi_value FROM MEASURE()

This step publishes Unbilled instances at four grains only: enterprise / payer / sold_to / site. Do not invent extra Unbilled grains (no product, no day, no bill-to). Values come FROM MEASURE(), not SUM(fct_unbilled).

First run: CREATE TABLE IF NOT EXISTS gold_kpi_value. Then replace-by-kpi_id: DELETE Unbilled gold rows, INSERT … MEASURE() … UNION ALL the four Unbilled grains. Never CREATE OR REPLACE the whole gold table - that wipes KPI 2/3. If the warehouse refuses INSERT from a Metric View, run the four MEASURE() queries and load those results. Still not a second SUM().

The replace-by-kpi_id shape (write this yourself; columns can match what you need to join and audit):

CREATE TABLE IF NOT EXISTS {{catalog}}.{{schema}}.gold_kpi_value (

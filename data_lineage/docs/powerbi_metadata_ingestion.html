Pipeline Overview

To capture and map the enterprise-wide report lineage, a robust, automated metadata ingestion pipeline was implemented. This pipeline bridges the Power BI workspace metadata with any existing full lineage in the knowledge graph.

Active Power BI Lineage Dashboard

The PowerBI workspace metadata ingested into the knowledge graph by this pipeline is originally consumed by the following active report: Open Active Power BI Lineage Report.

The ingestion lifecycle is separated into three distinct, robust stages:

1

High-Fidelity Extraction

Reads raw data extraction views from the source SQL databases containing datasets and workspace attributes. The tables are inner joined to pair active datasets directly with reports using the following SQL query:

SELECT 
    pbid.Workspace_Name, 
    pbir.Creator_Principal_Display_Name, 
    pbir.Report_Name, 
    pbid.Table_Name AS PBI_Table_Name, 
    pbid.Source_Text AS Expression,
    pbid.Connection_Type_Code, 
    pbid.Dataset_Id,   -- Added 'pbid.' here to prevent ambiguity
    pbid.Server_Name, 
    pbid.Database_File_Name AS [Database], -- Added brackets around Database
    pbid.Schema_Name, 
    pbid.View_Name, 
    pbir.State_Code, 
    pbir.Web_Url_Text, 
    pbir.Embed_Url_Text
FROM sem_internal_x.PowerBi_Dataset_Table_Dim_vw  pbid
INNER JOIN sem_internal_x.PowerBi_Report_Dim_vw  pbir
  ON pbid.Dataset_Id = pbir.Dataset_Id
WHERE Schema_Name IS NOT NULL 
  AND Schema_Name NOT IN ('None', 'nan', '')
  AND View_Name IS NOT NULL 
  AND View_Name NOT IN ('None', 'nan', '')
2

Conformance and View Resolution

Explodes multi-value cells, cleanses invalid placeholders, resolves schemas case-insensitively using live SQL catalog metadata, maps business areas, and derives appropriate Azure Synapse server endpoints.

3

Knowledge Graph Sync & Prune

Ingests conformed records into the Neo4j database using a 500-row transactional batch pattern and dynamically tags active nodes. It then executes structural pruning to eliminate orphan relationships or stale reports.

Conformance & Cleaning Rules

To prevent dirty or unstandardized metadata from polluting the graph model, the pipeline automatically executes a series of advanced conformance algorithms, mapping heuristics, and catalog-validation rules:

1. Multi-Value Array Splitting & Positional Exploding

When the raw SQL extraction returns records with multiple schema names or view names packed into single cells, the loader applies a standard regex pattern [,;\n\r\t/|] to identify the delimiters. It splits the cells into clean lists, trims whitespace, and explodes the records positionally into clean individual rows.

2. Live View Catalog Resolution (Mapping_Status)

To audit and catalog the conformed rows, the script queries the live SQL Server sys.views catalog to build a ground-truth map. Every exploded view name is validated case-insensitively, and one of three distinct statuses is assigned to the Mapping_Status column:

  • Clean: Assigned to rows that were already conformed at extraction time, requiring no splitting or array mapping.
  • Mapped: Assigned to exploded rows where the view name was successfully resolved and verified in the live sys.views SQL catalog under that schema.
  • Fallback (Not in Catalog): Assigned when the view name could not be found in the live view catalog. In this case, the system gracefully falls back to positional mapping or defaults to the first schema in the list to prevent dropping data.

3. Business Area Mapping Logic

To bridge technical database schemas with organizational structures, a schema-to-business-area lookup translates lowercase schema prefixes (e.g. sem_* or replica_*) into enterprise Business Areas. LSC examples:

  • Wholesale Marketing: Mapped from schemas like sem_wholesale, sem_wholesale_pricing, replica_helios, and replica_rightangle.
  • Pipelines & Terminals: Mapped from schemas like sem_supplychain, sem_supplychain_ops, and replica_atlas.
  • Manufacturing Operations: Mapped from schemas like sem_manufacturing, sem_manufacturing_ops, and replica_kestrel.
  • Finance: Mapped from schemas like sem_finance, sem_finance_kpi, and replica_orion.
  • Human Resources: Mapped from schemas like sem_hr, sem_hr_kpi, and sem_hr_ops.

4. Medallion Schema to IDP Server Defaults

If the raw server name or database name are empty/null, but the schema name matches standard IDP medallion patterns (such as starting with replica_, sem_, or ending in _core), they are mapped to standard production Azure Synapse defaults:
Server: lsc-idp-prod.sql.azuresynapse.net
Database: LSC Data Platform (IDP)

5. Invalidation & Placeholder Filtering

During data extraction, any rows with invalid schema or view names containing string placeholders such as 'None', 'nan', 'NULL', or empty strings are automatically filtered out and excluded from entering the ingestion pipeline.

Knowledge Graph Model

The conformed graph models the entire path from Person down to Server database structures without introducing non-standard node labels or visually cluttered hubs.

Conformed Database Schema Wiring

Person
─▶:HAS_ROLE
RoleAssignment
─▶:APPLIES_TO
Report
Report
─▶:CONSUMES
Table (View)
◀─:CONTAINS
Schema
◀─:HOSTS
DataSystem

Workspace Modeling: To keep the graph highly conformed and avoid clutter, Workspace_Name is modeled directly as a property (workspaceName) on the Report node itself rather than a separate hub node.

Uniqueness Constraint Merging: Because Table(qualifiedName) holds a strict uniqueness constraint, merging directly on multiple labels (e.g. MERGE (t:Table:View)) can cause Neo4j database validation errors if a node exists with only one label. We resolve this elegantly using a safe merging pattern: merge on the primary :Table label first, then apply SET t:View.

Transactional Ingestion Code

Below is the conformed Cypher ingestion statement executed transactionally in the notebook using 500-row batching:

// Ingest database nodes and report lineage
UNWIND $rows AS row

// 1. Server & Database Infrastructure
WITH row WHERE row.Server_Name IS NOT NULL AND row.Database IS NOT NULL
MERGE (srv:Server {serverName: row.Server_Name})
MERGE (ds:DataSystem {name: row.Database})
MERGE (srv)-[:HOSTS]->(ds)

// 2. Schema and Tables
WITH row, ds
WHERE row.Schema_Name IS NOT NULL AND row.View_Name IS NOT NULL
MERGE (sch:Schema {qualifiedName: row.Schema_Name})
ON CREATE SET sch.layer = "Semantic"
MERGE (ds)-[:HOSTS]->(sch)

MERGE (t:Table {qualifiedName: row.Schema_Name + '.' + row.View_Name})
ON CREATE SET t.name = row.View_Name,
              t.layer = "Semantic",
              t.createdAt = datetime()
ON MATCH SET t.updatedAt = datetime()
SET t:View
MERGE (sch)-[:CONTAINS]->(t)

// 3. Wire Business Area
WITH row, ds, sch, t
FOREACH (ba_name IN CASE WHEN row['Business Area'] IS NOT NULL THEN [row['Business Area']] ELSE [] END |
    MERGE (ba:BusinessArea {name: ba_name})
    MERGE (ds)-[:BELONGS_TO]->(ba)
    MERGE (sch)-[:BELONGS_TO]->(ba)
)

// 4. Power BI Report
WITH row, t
MERGE (rpt:Report {name: row.Report_Name})
ON CREATE SET rpt.connectionType = row.Connection_Type_Code,
              rpt.webUrl = row.Web_Url_Text,
              rpt.state = row.State_Code,
              rpt.workspaceName = row.Workspace_Name,
              rpt.lastSeen = datetime($runStart),
              rpt.createdAt = datetime()
ON MATCH SET rpt.connectionType = row.Connection_Type_Code,
             rpt.webUrl = row.Web_Url_Text,
             rpt.state = row.State_Code,
             rpt.workspaceName = row.Workspace_Name,
             rpt.lastSeen = datetime($runStart),
             rpt.updatedAt = datetime()

// 5. Report Creator Role Assignment
FOREACH (creator IN CASE WHEN row.Creator_Principal_Display_Name IS NOT NULL THEN [row.Creator_Principal_Display_Name] ELSE [] END |
    MERGE (p:Person {name: creator})
    MERGE (ra:RoleAssignment {type: "Report Creator", scope: row.Report_Name})
    ON CREATE SET ra.status = "Active", ra.createdAt = datetime()
    MERGE (p)-[:HAS_ROLE]->(ra)
    MERGE (ra)-[:APPLIES_TO]->(rpt)
)

// 6. Lineage link (CONSUMES)
MERGE (rpt)-[con:CONSUMES]->(t)
ON CREATE SET con.expression = row.Expression,
              con.lastSeen = datetime($runStart),
              con.createdAt = datetime()
ON MATCH SET con.expression = row.Expression,
             con.lastSeen = datetime($runStart),
             con.updatedAt = datetime()

Stale Pruning (State Sync)

Because report deployments and workspace contents evolve rapidly, we use a Sync and Prune design to systematically delete relationships and reports that have disappeared from the source databases.

Multi-Source Safe Isolation Guarantee

To prevent the pruning process from accidentally affecting or deleting Report nodes or relationships loaded by other ingestion scripts or distinct projects, both the Report nodes and the CONSUMES edges loaded by this script are tagged with source: "PowerBI_Workspace". The sync-and-prune queries are strictly constrained to this namespace, leaving all other graph data completely safe and untouched.

  1. The run captures a UTC timestamp at the start of the job (runStart = datetime.now(timezone.utc).isoformat()).
  2. Every successfully processed Report and CONSUMES relationship has its lastSeen property updated to this exact timestamp and tagged with source: "PowerBI_Workspace".
  3. After ingestion completes, only the CONSUMES edges and Report nodes that belong to this namespace (source: "PowerBI_Workspace") and whose lastSeen is less than the run start time (or null) are pruned:
// Delete only stale Power BI workspace consumption edges
MATCH (rpt:Report {source: "PowerBI_Workspace"})-[con:CONSUMES {source: "PowerBI_Workspace"}]->(t:Table)
WHERE con.lastSeen < datetime($runStart) OR con.lastSeen IS NULL
DELETE con

// Delete only stale Power BI workspace report nodes
MATCH (rpt:Report {source: "PowerBI_Workspace"})
WHERE rpt.lastSeen < datetime($runStart) OR rpt.lastSeen IS NULL
DETACH DELETE rpt

Reproducing Ingestion

To refresh the Power BI lineage or run the ingestion again, follow these exact steps using the production-grade load script:

A

Activate the Virtual Environment

Open your terminal in the project root directory and activate the virtual environment:
.venv\Scripts\activate

B

Run the Standalone Script

Execute the conformed load script directly from your terminal:
python src/load_powerbi_lineage.py

C

MFA Authentication

An interactive browser window will pop up prompting you to authenticate your SQL Server connection via MFA. Once authenticated, the script will automatically clean, explode, map, and transactionally load the conformed lineage to Neo4j, followed by structural pruning of stale nodes.

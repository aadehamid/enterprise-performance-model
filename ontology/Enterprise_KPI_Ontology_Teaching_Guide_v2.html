Part 1

Why an ontology at all — the problem it solves

Start with the pain you already know from the Tableau-to-Power BI migration: two reports both show a number called throughput, the formulas differ slightly, and nobody can say authoritatively which is right, who owns it, or where the numbers physically come from. The meaning of the KPI lives in people's heads, in scattered spreadsheets, and inside BI tool config files — none of which a machine (or a new colleague) can query.

An ontology is the fix for exactly that. In plain language: an ontology is a formal, machine-readable map of the concepts in a domain and the relationships between them. Not a database of KPI values, and not a document about KPIs — a graph of meaning, where "Rack Price Capture Rate % is a KPI, defined by certified definition v1, owned by the Commercial Pricing Manager, computed from Realized Rack Revenue, which comes from a gold dataset, which came from RightAngle CTRM's NET_PRICE_PER_GAL field" are all explicit, traversable, checkable facts.

The one-sentence intuition A relational database stores values in tables you design up front. An ontology stores meaning as a graph of small facts, so questions you never anticipated — "if this source field changes, which dashboards break?" — can still be answered by walking the graph.

And — new in v2.0.0 — the ontology now also stores facts over time: not just "how is this KPI defined" but "what did it actually read at Beaumont Terminal 1 on July 31st, and was that a breach?" That addition (the observation layer, Parts 7–10) came from a hard lesson about what was missing from the first version.

What the KPI ontology is a map of

The design carves the domain into six modules, each answering one governance question. Keep this table in your pocket — the entire .ttl file is these six modules plus the "bridges" between them.

#ModuleThe question it answers
1Business ArchitectureWhy does this KPI exist, and who in the business cares?
2KPI Model — specification layerWhat exactly is being measured, how, and against what target?
2aKPI Model — observation / fact layer new in v2What did it actually read — where, when, and was it on target?
3Semantic ModelWhat is the one governed, reusable definition consumers should bind to?
4Lineage & Data ArchitectureWhere did the numbers physically come from, and how were they transformed?
5ConsumptionWhere does the KPI actually show up for a human?
6GovernanceWho owns / approved / certified this, and can we audit it?

One crucial change from v1.0.0: these modules are now recorded as metadata tags, not as superclasses. That distinction — the difference between "grouped together" and "the same kind of thing" — turned out to be the single biggest lesson of the whole project, and Part 7 tells that story in full.

Notice, too, that these are the same questions the EPM charter asks of every KPI ("why does a KPI exist, how it is calculated, which process it measures, which data products support it, who is accountable"). The ontology is one candidate technical representation of that ambition.

Part 2

The three-layer stack: RDF → RDFS/OWL → Turtle

This is the single distinction that trips up almost every beginner, so we settle it first. Three different things are stacked on top of each other, and each answers a different question:

LayerWhat it isQuestion it answersExample
RDF
the data model		A way of describing anything as a graph of three-part facts ("triples")"What is a fact, structurally?"subject – predicate – object
RDFS / OWL
the ontology languages		Vocabularies written in RDF for declaring kinds of things, hierarchies, and logical rules"What kinds of things exist, and what can be inferred?""KPI is a subclass of Metric"; "every KPI must have a definition and an owner"
Turtle
the text syntax		One human-friendly notation for writing triples down as text"How do I type it?"ekpi:KPI rdfs:subClassOf ekpi:Metric .
2.1 — Why RDF: everything is a triple

RDF (Resource Description Framework) says: any knowledge, no matter how complex, can be broken into atomic three-part statements — subject, predicate, object. Each triple is one labeled edge in a graph:

data:RackPriceCaptureRateKPI ekpi:alignsToObjective data:ImproveRackCapture99pctQ4FY26
data:RackPriceCaptureRateKPI ekpi:hasUnitOfMeasure data:PercentUnit

Stack thousands of these and you have an enterprise knowledge graph. Why choose this over tables? Three reasons:

1. Merge without collisions. Every subject, predicate, and object is a globally unique identifier (an IRI — Part 3), so two graphs built by different teams can be poured into one pot and nothing clashes. Try that with two databases that both have a KPI table.

2. Schema-later, not schema-never. New relationships are just new triples. You don't run ALTER TABLE to add "KPI supports value stream"; you assert one more fact. This is what makes the progressive metadata enrichment the EPM charter demands technically natural — empty slots are simply triples not yet asserted. The v2.0.0 observation layer proved this in practice: an entire new fact layer was added without restructuring anything that existed.

3. The question set is open. Because the data is a graph, any path query works: KPI → dataset → source field, or backwards. In tables, every new traversal is a new set of joins someone has to design.

Analogy for graph-database users: RDF triples are like Neo4j's (node)-[:REL]->(node), with two additions — the object may be a plain value like "98.4", and every name is globally addressable so graphs merge safely.

2.2 — Why RDFS and OWL: raw triples have no rules

Plain RDF lets you assert anything: "Tuesday owns the color blue" is a perfectly legal triple. RDF gives you a fact format, not fact discipline. That's where the two ontology languages come in — both are themselves just vocabularies of special, standardized predicates you use inside ordinary triples:

RDFS (RDF Schema) is the light layer: it lets you declare classes (rdfs:Class), build hierarchies of classes (rdfs:subClassOf) and now of properties too (rdfs:subPropertyOf, new in v2.0.0), attach human-readable names (rdfs:label, rdfs:comment), and give properties a "function signature" (rdfs:domain, rdfs:range). Think of RDFS as the ability to draw a class diagram.

OWL (Web Ontology Language) is the power layer on top. It adds real logic — the things RDFS cannot say:

OWL featureWhat it lets you sayUsed in our ontology for
owl:Restriction + someValuesFrom"Every member of this class must have at least one of these"Every KPI needs a definition and an owner; every Silver dataset must trace to a Raw dataset (six restrictions total in v2.0.0)
owl:FunctionalProperty"A thing can have at most one value for this property"One current certification status per definition; one status per observation
owl:disjointWith"Nothing can belong to both of these classes"A dataset can't be Raw and Gold at the same time
owl:equivalentClass"This class means exactly this logical expression"CertifiedDefinition = KPIDefinition whose status = Certified (inferred!)
owl:oneOf"This class contains only this closed list of members"Five closed vocabularies: CertificationStatus, Criticality, ThresholdSeverity, AggregationType, ObservationStatus
owl:inverseOf"These two properties are the same edge read both ways"hasDefinition / isDefinitionOf; feedsSemanticModel / isFedBy

Why OWL matters, in one sentence: it turns your model from documentation into something a reasoner — a logic engine — can check ("this dataset is typed both Raw and Gold, that's an error"; "this Gold dataset feeds no semantic model, that's a violation") and extend ("this definition's status is Certified, therefore it is a CertifiedDefinition, no manual tagging needed"). Governance rules become executable, not aspirational. The v2.0.0 review (Part 7) leaned on exactly this: several distinctions that lived only in comments were promoted into restrictions a reasoner can actually verify.

2.3 — Why Turtle: the readable way to write it down

Turtle ("Terse RDF Triple Language") is purely a file format — one of several text notations for the identical graph. The alternatives are RDF/XML (verbose, older), JSON-LD (JSON-shaped, good for web APIs), and N-Triples (one full triple per line, good for machines, brutal for humans). Turtle is the standard choice for authoring ontologies because it reads closest to natural sentences.

Key mental move The syntax is disposable; the graph is what persists. You could regenerate this exact ontology as JSON-LD tomorrow and its meaning would be bit-for-bit identical. When you read Turtle, always translate in your head back to triples: subject — predicate — object.

One more thing Turtle is not: proof of correctness. A file can parse perfectly and still model the domain wrongly — that gap between "compiles" and "is actually right" is the entire subject of Part 7.

Part 3

Names that never collide: IRIs, namespaces, prefixes

Every node and edge in RDF needs a name, and RDF insists the name be globally unique. The mechanism is the IRI (Internationalized Resource Identifier) — think "a URL that names a concept, not necessarily a webpage you visit":

https://ontology.enterprise.example.com/kpi-store/core#KPI

Two companies can both have a concept called "KPI"; because the IRIs differ, their graphs can be merged and never collide. That is the whole trick — uniqueness by web address, and using a domain you control means no one else can accidentally mint the same name.

Prefixes: nicknames for namespaces

Typing full IRIs constantly would be unreadable, so Turtle lets you declare a prefix — a short alias for a namespace (the common "stem" shared by a family of IRIs):

@prefix ekpi: <https://ontology.enterprise.example.com/kpi-store/core#> .

After this line, ekpi:KPI expands to the full IRI above. It is exactly like import numpy as np in Python — np is not numpy, it's a nickname that expands back to the full thing.

The most important design choice in the file: two custom namespaces, not one

Our ontology declares two namespaces of its own, and keeping them separate is deliberate enterprise hygiene:

NamespacePrefixHoldsChanges when…
…/kpi-store/core#ekpi:The schema — every class and property we invented (KPI, KPIObservation, GoldLayerDataset, hasDefinition…)The model of the world changes — rare, versioned, governed
…data.enterprise…/kpi-store/data:The individuals — actual KPIs, datasets, teams, approval events, daily observationsThe facts about the world change — daily, loaded and reloaded freely
Why this split matters Instance data (data:) can be loaded, reloaded, or swapped wholesale without ever touching a class or property definition (ekpi:). It's the same instinct as separating a database's DDL from its rows — the schema is a stable contract, the data is a flowing stream. The new observation layer makes this concrete: KPI readings will arrive every day as new data: individuals, while the ekpi: schema never moves. Throughout this document, teal = schema, amber = individuals, so you can see the split at a glance.

Monolithic today, modular tomorrow

The blueprint reserves six module sub-namespaces (ba:, kpim:, sem:, lin:, cons:, gov:) for a future physical split into one .ttl file per module, each importing a shared core.ttl via owl:imports. None of that is in use today — the current file is deliberately one file, one ekpi: namespace, which is easier to learn from and to review. Treat the split as a documented roadmap, not the current state; the module tags (Part 9.9) already mark where the seams would go.

Versioning: how v2.0.0 announces itself

The ontology's main IRI carries no version number (so references stay stable). Instead the header asserts owl:versionInfo "2.0.0", a dated owl:versionIRI snapshot (…/core/2026-08-02#), and — new — owl:priorVersion pointing back at the v1.0.0 snapshot (…/core/2026-08-01#). The "current" address always works; every historical version remains addressable, and the chain of versions is itself machine-readable — the same instinct as the EPM rule that approved baselines can't change silently.

Part 4

The ten borrowed vocabularies — and why reuse beats reinvention

Open the .ttl file and the first thing you see is ten @prefix lines besides our own two. Each is a standard vocabulary — a published set of classes and properties the wider world already agrees on. The design rule at work: never invent a term when a well-known standard already has one. Every reused term is a free integration: any tool that already speaks PROV, SKOS, or FOAF partially understands our graph with zero custom code. In v2.0.0 three of these vocabularies took on new jobs — marked below.

Why the SKOS, PROV, and FOAF choices are the clever ones

SKOS for the glossary — and now for grouping: business terms could have been modeled as OWL classes, but SKOS is purpose-built for term lists — skos:altLabel carries the synonyms "Rack Margin Capture" and "Price Realization Rate" for "Rack Price Capture Rate" with no extra machinery (this is also why the old Synonym class was deleted: SKOS already did its job). And v2.0.0 discovered a second SKOS gift: skos:Collection means exactly "a group of things with no implied shared essence" — precisely the semantics a documentation module needs, which is why it replaced the bucket superclasses.

PROV for lineage: instead of inventing a "cameFrom" predicate, every layer-to-layer hop reuses prov:wasDerivedFrom. Any lineage visualizer or catalog that understands the W3C provenance standard can render our raw→silver→gold chains automatically, with zero mapping work. Reuse is the integration strategy.

FOAF for agency: before v2.0.0, Role floated with no upper anchor — nothing declared that owners and stewards are things that can act. One line (ekpi:Role rdfs:subClassOf foaf:Agent) fixes that, and means any FOAF-aware system (an HR or identity graph, say) understands our roles without a bespoke mapping.

Part 5

Turtle syntax crash course — every symbol explained

Turtle has a tiny grammar. Master seven punctuation marks and three literal decorations and you can read the entire 1,400-line file. A v2.0.0 Turtle file reads top to bottom in this order: prefixes → ontology metadata → module tags → classes → properties → individuals.

5.1 — The shape of every block: ; , .
SUBJECT
    predicate1  object1 ;
    predicate2  object2 ;
    predicate3  objectA, objectB .
SymbolRead it as
;"Same subject — here's the next fact about it." (Saves retyping the subject.)
,"Same subject and same predicate — another object." One line, multiple triples.
."End of this subject's block. No more facts about it here."

So the block above is five triples: (S,p1,o1), (S,p2,o2), (S,p3,oA), (S,p3,oB) — the punctuation is pure compression, nothing more. When in doubt while reading, mentally expand back to one triple per line. A real example of the comma at work, from the observation layer: ekpi:observedForDimensionValue data:HoustonRackTerminal3, data:ULSDDieselProduct — one line, two triples, "this reading applies to that terminal and that product."

5.2 — a : the most important two letters in the file
ekpi:KPI a owl:Class .
data:RackPriceCaptureRateKPI a ekpi:KPI .

a is Turtle shorthand for the predicate rdf:type — read it as "is a". The two lines above are doing very different jobs with identical syntax, and seeing the difference is the moment ontology "clicks":

Line 1 says the concept KPI is a class — a category of things. Line 2 says one specific thing, Rack Price Capture Rate %, is an individual (an instance) belonging to that category. Schema vs data — teal vs amber — in two lines.

5.3 — Literals: quoted values, @en language tags, ^^xsd: typing
data:Target_99pct_Q4FY26 a ekpi:Target ;
    rdfs:label "Target 99% FY26 Q4"@en ;
    ekpi:targetValue "99.0"^^xsd:decimal ;
    ekpi:targetPeriod data:FY26_Q4 .

A literal is a plain value — text, number, date — sitting at the object position instead of another node. Three decorations:

"…" — everything in RDF starts life as quoted text. An undecorated string like "KPI-COM-001" defaults to xsd:string.

@en — a language tag: "this text is English." It's what makes multilingual ontologies possible — add rdfs:label "KPI"@de later without touching anything.

^^xsd:decimal — a datatype suffix: "interpret this text as a decimal number." It's RDF's type-cast. Without it, "99.0" is just characters a machine can't compare or do math on. Same pattern: "2026-07-31"^^xsd:date, "2026-07-15T09:00:00"^^xsd:dateTime.

Note the fourth line: targetPeriod points at a node (data:FY26_Q4, a TimePeriod individual with real start/end dates), not a literal. In v1.0.0 this property was documented but never implemented — one of the drift bugs the review caught (Part 7, lesson 4).

5.4 — [ … ] blank nodes: anonymous helper nodes
ekpi:KPI rdfs:subClassOf [
    a owl:Restriction ;
    owl:onProperty ekpi:ownedBy ;
    owl:someValuesFrom ekpi:BusinessOwner
] .

Square brackets create a blank node — an unnamed resource that exists only to hold a bundle of facts. It gets no IRI because nothing else in the graph will ever need to point at it; it's a throwaway helper. Here it holds an OWL restriction (this particular one — every KPI must have an owner — is new in v2.0.0 and is decoded fully in Part 9). Intuition: it's the anonymous inner object in JSON — {"onProperty": …, "someValuesFrom": …} — versus a named, addressable record.

5.5 — ( … ) lists: ordered collections
owl:oneOf ( data:ObsStatus_OnTarget data:ObsStatus_Watch data:ObsStatus_Breach )

Parentheses build an RDF list — an ordered collection, used where OWL needs "exactly these, as a set": enumerations (owl:oneOf) and intersections (owl:intersectionOf). Note there are no commas inside the parentheses — items are space-separated. The example above closes the new ObservationStatus vocabulary: an observation is OnTarget, Watch, or Breach, and can never be anything else.

5.6 — # comments and < > full IRIs

# like this — everything after a hash (outside an IRI) to end of line is a comment for humans; parsers ignore it. The big banner blocks in the .ttl file are just comments used as section dividers — the v2.0.0 file even carries its own nine-point changelog as a comment banner at the top.

<https://…> — angle brackets always mean "this is a full, literal IRI, not a prefixed shorthand." You see them in @prefix declarations and in the ontology header, where the ontology names itself by its own full IRI.

One caution the review reinforced (Part 7, lesson 9): a comment is documentation, never the sole carrier of a queryable fact. In v1.0.0 the KPI's SQL lived only inside an rdfs:comment; v2.0.0 promoted it into a real logicExpression datatype property and kept the comment as a human gloss.

5.7 — The beginner trap: rdfs:subClassOf is for classes only
ekpi:StrategicObjective a owl:Class ;
    rdfs:subClassOf ekpi:BusinessGoal .        # CLASS level: every objective IS a goal-type thing

data:ImproveRackCapture99pctQ4FY26 a ekpi:StrategicObjective ;
    ekpi:narrowsGoal data:ProtectGrowCommercialMarginGoal .   # INSTANCE level: this objective narrows that goal

Both use the idea of "narrower," but at different layers. rdfs:subClassOf only ever connects two classes ("every member of A is also a member of B"). To connect two individuals, you need an ordinary object property — here, the purpose-built ekpi:narrowsGoal (which in v1.0.0 existed only in prose; now it's a real property with a real asserted edge). Using subClassOf between two specific named things is the most common beginner error in OWL — and, as Part 7 shows, misusing subClassOf between things that merely share a topic is its equally common grown-up sibling.

Part 6

How the ontology was designed — the Stage 1 method, step by step

The .ttl file wasn't typed top to bottom. It was designed first (Stage 1, on paper), serialized into Turtle (Stage 2), and then — critically — reviewed and corrected (the v1.0.0 → v2.0.0 cycle, Part 7). This part covers the design method; it is the part you can reuse for any future domain:

Step 1 — Partition the domain into modules

Before any class exists, decide the big shapes. The six modules from Part 1 were chosen so each answers exactly one governance question and can stand alone — a team can adopt Lineage without adopting Consumption. Modules are stitched together by a small set of deliberate bridge properties (like ekpi:realizesKPI, which connects the Semantic Model module to the KPI module). Why: modularity is what lets the ontology grow incrementally instead of being a big-bang design — the same "progressive enrichment" logic as the EPM delivery sequence. The v2 refinement: module membership is metadata (dcterms:isPartOf), never a superclass — the full story is Part 7, lesson 1.

Step 2 — Name the classes (the nouns)

Within each module, list the categories of things — the nouns of the domain. Business Architecture gets BusinessCapability, ValueStream, BusinessDomain, BusinessProcess, BusinessGoal…; the KPI module gets KPI, KPIDefinition, Measure, Metric, Target, Threshold, Dimension, Grain — and, in v2.0.0, the fact-layer nouns KPIObservation, DimensionValue, ObservationStatus. Each class gets a one-line, plain-English definition before any syntax is written. Why: if you can't define the class in a sentence, you don't yet know whether it should exist. (And if you can't instantiate it in a worked example, it may not deserve to exist — the fate of Synonym and LineageEdge.)

Step 3 — Build the hierarchy — but only where it's honestly a hierarchy

Three hierarchy decisions carry real meaning:

KPI ⊑ Metric ⊑ PerformanceIndicator. "Every KPI is a Metric, but not every Metric is governed and strategic enough to be a KPI" — the EPM taxonomy principle, encoded. And v2.0.0 made the difference operational: a KPI is now formally required (by restriction) to have a definition and a BusinessOwner; a Metric is not. A reasoner can tell them apart from asserted facts alone.

Dataset as a genuine abstraction. ekpi:Dataset survives because every member truly is "a dataset at some medallion layer" — and because hasQualityRule/transformedBy get declared once instead of three times, and owl:disjointWith only makes sense between siblings under a real shared parent.

Everything else is a tag, not a parent. The bracketed module names are skos:Collection individuals reached by dcterms:isPartOf. Why the old bucket superclasses were demoted is the opening lesson of Part 7.

Step 4 — Name the properties (the verbs), with domain → range — and now a hierarchy of their own

Now connect the nouns. Every relationship gets a name, a domain (what kind of thing sits on the left) and a range (what kind sits on the right) — literally a function signature: hasDefinition: KPI → KPIDefinition. Object properties link things to things; datatype properties link things to plain values (targetValue: Target → xsd:decimal). Why domain/range matter: they are lightweight guardrails — tools can flag a triple whose subject or object is the wrong kind of thing, and editors can auto-suggest valid connections.

New in v2.0.0: once you have ~35 properties, organize them too. Three super-properties (hasSpecificationElement, hasGovernanceRecord, hasSemanticComponent) group the narrow predicates via rdfs:subPropertyOf — decoded in Part 9.2.

Step 5 — Add constraints only where they pay rent

OWL can express elaborate logic; the design uses it sparingly — every constraint in the file exists because it catches a specific real-world governance failure:

Constraint chosenThe failure it prevents
KPI must have ≥1 definition (someValuesFrom)"Orphan" KPIs on dashboards with no documented definition — the exact post-migration gap
KPI must have ≥1 BusinessOwner newUngoverned numbers masquerading as KPIs — this restriction is the checkable KPI-vs-Metric line
Raw must derive from a SourceField; Silver from Raw; Gold must feed a SemanticModel newMedallion order enforced by logic, not naming convention — a Gold dataset that dead-ends is now a flagged violation
hasCertificationStatus and hasObservationStatus are functionalA definition simultaneously Draft and Certified; an observation both OnTarget and Breach
Five closed owl:oneOf vocabularies 3 newFree-text drift: "High" vs "high" vs "Critical"; "SUM" vs "Sum" vs "total"
CertifiedDefinition defined by equivalentClassTrust labels drifting out of sync with actual status — membership is inferred, never hand-maintained

Equally important is what was not constrained: a formula may have multiple calculation implementations (SQL and DAX legitimately coexist), so no hard cardinality was placed on implementedBy. Over-constraining a graph that must reflect messy reality is its own failure mode.

Step 6 — Decide namespaces, reuse, and file layout

Finally the packaging decisions from Parts 3 and 4: split ekpi: (schema) from data: (individuals); reuse SKOS for the glossary and for module collections, PROV for lineage, FOAF for agency; hash IRIs for terms, slash IRIs for instances; version via owl:versionInfo/versionIRI/priorVersion, not the path. The one-file-per-module split (each importing a shared core.ttl, bridge properties living in core to avoid circular imports) stays a documented future state.

The method in one line Modules → nouns → honest tree → verbs (with signatures and their own hierarchy) → just-enough constraints → packaging — then review against reality (Part 7). Design on paper, serialize last, and never confuse "it parses" with "it's right."
Part 7

The review that produced v2.0.0 — eleven lessons in honest modeling

This is the newest and, for learning purposes, most valuable material in the whole package. v1.0.0 parsed perfectly and looked plausible — and a structured review (modeled on ontologist Casey Hart's critique of a ChatGPT-generated real-estate ontology, "I Asked ChatGPT to Build an Ontology. Here's What Happened.") found the identical failure modes in our own file, in our own domain's clothing. The gap between an ontology that compiles and one that models the domain correctly is exactly where human judgment does the work.

The core discipline: two questions, never confused

Question 1 — "Is this a genuine kind of that thing?" This is what rdfs:subClassOf answers. It is a logical claim: every member of the subclass really is a member of the superclass, always, in every context.

Question 2 — "Do I just want to group these for browsing, documentation, or module ownership?" A metadata question — and it must never be answered with subClassOf.

Nearly every mistake below is, underneath, a case of reaching for the taxonomy tool to solve a grouping or labeling problem. Internalize this one distinction and the rest of the review is just its consequences worked out across the file.

Lesson 1 — The "genuine kind" test: no bucket superclasses

Hart's version: the generated ontology's top class Property had Address, Parcel, Building, Listing, and Transaction as subclasses — things related to a property, not themselves properties. His memorable test: would you put a bedroom and a shoe in the same class because they're both "things in a house"?

Our version: v1.0.0 had four bucket superclasses — BusinessArchitectureElement, SemanticAsset, LineageNode, GovernanceElement — invented purely to mirror the documentation modules. But a BusinessCapability and an OrganizationalUnit are simply not the same kind of thing; a semantic model, an attribute, a glossary term, and a mapping rule share a topic, not an essence. Asserting subClassOf made a false logical claim to buy a convenient grouping label.

The fix: all four buckets removed. Three superclasses survived because they honestly pass the test: ConsumptionAsset (every member really is "a surface a human consumes KPI values through"), PerformanceIndicator (every member really is "a quantification of performance"), and Dataset (every member really is "a dataset at some medallion layer" — and disjointness between Raw/Silver/Gold only means something between siblings under a real parent).

The standing rule: before writing any abstract superclass whose only job is grouping, ask out loud: "is every member always and necessarily that kind of thing, no exceptions?" If the honest answer is "well, they're related to the same topic" — that's a grouping, and the next lesson has the right tool.

Lesson 2 — Group honestly: dcterms:isPartOf + skos:Collection
ekpi:BusinessArchitectureModule a skos:Collection ;
    rdfs:label "Business Architecture Module"@en .

ekpi:BusinessCapability a owl:Class ;
    dcterms:isPartOf ekpi:BusinessArchitectureModule ;
    rdfs:label "Business Capability"@en .

Decode: the first block mints an individual (not a class!) whose whole job is to be a labeled bucket — skos:Collection exists precisely for "a group of things with no implied shared essence." The second block files BusinessCapability under that bucket with dcterms:isPartOf — a plain metadata fact. Every one of the ~50 classes in the file carries exactly one such tag.

What you lose: nothing. "Show me everything in the Lineage module" is still one easy query — you match dcterms:isPartOf ekpi:LineageModule instead of rdfs:subClassOf ekpi:LineageNode. The query is equally simple; the difference is the ontology no longer asserts something untrue to make it possible. Note also that the two mechanisms coexist happily: GoldLayerDataset is both rdfs:subClassOf Dataset (a kind claim) and dcterms:isPartOf LineageModule (a filing claim) — different purposes, no conflict.

Lesson 3 — Model measurements as events, not attributes: the Observation layer

Hart's version: the generated ontology modeled the property's sale as an oddly-nested attribute rather than its own event with a value, unit, and date — quietly blocking the query he most cared about: comparing sales over time.

Our version — the single biggest gap in v1.0.0: the graph could fully describe how a KPI is defined, its lineage, and its governance… and had no class for what it actually measured. It could answer "what is Rack Price Capture Rate and where does its data come from" but not "what was it at Beaumont Terminal 1 last Tuesday, and was it above target?" — which is the entire point of a KPI store.

The fix — the Observation/Fact pattern, three new classes: KPIObservation (one dated, dimensioned, valued reading), DimensionValue (a specific value on an axis — "Houston Rack Terminal 3" — as distinct from Dimension, the axis itself, "Terminal"), and the closed ObservationStatus vocabulary (OnTarget / Watch / Breach). Part 8 §7 and Part 10 show it live, including a deliberately unhealthy reading in Breach — the graph must represent bad news, not just the happy path.

The standing rule: anything that happens repeatedly over time and needs comparing across occurrences (a sale, a reading, a shift's output, a KPI value) gets its own event/fact class from day one. Never nest it as an attribute on the static definition — that structurally blocks the time-series queries the domain will certainly need.

Lesson 4 — Audit design docs against implementation: no silent drift, no orphans

A literal side-by-side audit of Stage 1 (the narrative) against Stage 2 (the Turtle) found real drift: targetPeriod documented but never implemented; TimePeriod a full documented class with zero individuals; Synonym and SemanticRelationship declared but never instantiated or connected (pure orphans); ValueStream, BusinessFunction, ProcessStep, DataProduct, AnalyticalModel, AccessRule, OrganizationalUnit declared but untested; StewardshipAssignment's one individual carrying nothing but a label — an inert placeholder.

The fix, item by item: targetPeriod implemented as a real object property wired to real TimePeriod individuals; Synonym deleted (its whole job was already done by skos:altLabel — modeling one idea twice is redundancy, not richness); LineageEdge deleted (fully covered by reused PROV edges); every surviving class given at least one working individual in the worked example; StewardshipAssignment given real properties (next lesson but one shows it working).

The standing rule: before calling an ontology "done," walk both directions: every design-doc term must exist and be used in the Turtle; every Turtle term must match its design-doc description. Anything declared-but-unused gets removed, implemented, or explicitly flagged "future extension" — never left to silently imply coverage that doesn't exist.

Lesson 5 — Back every meaningful subclass distinction with a restriction

Hart's version: Bedroom had a label and a comment, but nothing said what actually makes a room a bedroom. A human reading the comment understands; a reasoner cannot.

Our version: nothing beyond prose distinguished a KPI from a plain Metric, or said why Gold differs from Silver (disjointness says they're exclusive, not why). The fix: five new restrictions — KPI requires an owner; Raw requires derivation from a SourceField; Silver from Raw; Gold must feed a SemanticModel (all decoded in Part 9.5). Now "which KPIs have no owner?" and "which Gold datasets dead-end?" are reasoner-checkable violations, not hopes.

The standing rule: a comment describing what makes a subclass different is a starting point, not an ending point. Ask: "could a reasoner tell these two classes apart from asserted facts alone?" If not, add the restriction.

Lesson 6 — Give properties a hierarchy too

~35 object properties sat completely flat in v1.0.0. But hasFormula, hasTarget, hasThreshold, hasGrain… are conceptually siblings — each is "a piece of a KPI's specification" — and the graph offered no way to ask "everything that specifies this KPI" without hand-listing seven predicates. The fix: three super-properties via rdfs:subPropertyOf (hasSpecificationElement, hasGovernanceRecord, hasSemanticComponent) — mechanics in Part 9.2.

Lesson 7 — Close free-text fields into controlled vocabularies

Hart's version: underspecified terms ("city" — a string? a geographic entity?) get interpreted inconsistently by different users. Our version: we'd correctly closed CertificationStatus but left criticality, thresholdSeverity, and aggregationType as free xsd:string — inviting "High" vs "high" vs "Critical", "SUM" vs "Sum" vs "total". The fix: all three closed with owl:oneOf over named individuals (plus the new ObservationStatus), turning "find every record with an invalid value" from a monitoring problem into a structural impossibility. Note the ripple effect: criticality changed from a datatype property to an object property, because its value is now a governed individual, not a string.

Lesson 8 — Write competency questions, before and after

Good ontology engineering starts from "what will people actually need to query" and checks the vocabulary against that list — not eventually, but as a design input. v1.0.0 listed benefits qualitatively ("supports impact analysis") but never wrote a checkable question list; had it done so, "what was this KPI's value at this terminal on this date?" would have exposed the missing Observation layer months earlier. v2.0.0 ships fifteen concrete competency questions (Part 12), each traceable end-to-end through the current classes and properties.

Lesson 9 — Promote facts out of comments — but don't destroy useful "redundancy"

First half: the KPI's SQL lived only inside an rdfs:comment — unqueryable, uncomparable. Promoted to a real logicExpression datatype property; the comment stays as a human gloss. Rule: anything a person might filter, compare, or query on is a structured property, never comment prose.

Second half — the subtler lesson: the property-hierarchy pass surfaced what looked like duplication: stewardedBy (KPI → steward, directly) and hasStewardshipAssignment → a full StewardshipAssignment record. The instinct is to collapse them. Deliberately, both were kept, because they answer different questions: stewardedBy answers "who do I ask right now" in one cheap hop (a dashboard tooltip); the assignment record answers "who has been steward, over which date ranges" — auditable history the shortcut structurally cannot carry once a steward changes. Rule: keep a shortcut only if it serves a query the authoritative record makes expensive; keep the record only if it captures what the shortcut cannot (here: time-boundedness) — and document why, so a future reviewer doesn't "fix" it away.

Lesson 10 — Anchor local root classes to a recognized upper concept

Owners and stewards were subclasses of a local Role class that floated with no upper anchor — the "this is a thing capable of acting, owning, approving" semantics were implicit. One line fixes it: ekpi:Role rdfs:subClassOf foaf:Agent. Now any FOAF-aware tool understands our roles are agents, no bespoke explanation needed. Rule: before inventing a local root for people/orgs/systems that act, check whether foaf:Agent, prov:Agent, or similar already has the concept.

Lesson 11 — Use SKOS labeling consistently, and only where it earns its keep

v1.0.0 used skos:prefLabel/altLabel/definition on exactly one showcase class (BusinessTerm) and nowhere else. The fix is pragmatic, not maximal: extend skos:altLabel to the handful of terms that genuinely have alternate names, without ceremonially SKOS-ifying classes nobody calls by a second name. Rule: apply SKOS wherever a real synonym or preferred/informal split exists — consistently, but never as decoration.

The reviewer's checklist, in one breath Genuine-kind test on every subClassOf · groupings via isPartOf + Collection · repeated happenings get an event/fact class · no design-vs-implementation drift, no orphans · every distinction backed by a restriction · properties get a hierarchy · governed value sets closed with oneOf · competency questions written and traced · queryable facts out of comments (but honest shortcut/record pairs kept) · actors anchored to foaf:Agent · SKOS where real synonyms live. Run it before signing off on any ontology — this one or the next.

Part 9

The nine OWL & RDFS power tools — each one fully decoded

These are the places where the ontology goes beyond "labeled boxes and arrows" into actual logic and honest structure. Master these nine and you've mastered every advanced construct in the file. Two are new to v2.0.0.

9.1 — rdfs:subClassOf: inheritance and inference in one — used honestly

"Every member of class A is also a member of class B." Its power is that a reasoner applies it automatically: assert data:RackPriceCaptureRateKPI a ekpi:KPI once, and because KPI ⊑ Metric ⊑ PerformanceIndicator, the individual is also a Metric and a PerformanceIndicator — zero extra triples; queries for "all metrics" find your KPIs for free. The v2 discipline: this is a logical claim, reserved for genuine kinds (Part 7, lesson 1). When you merely want to group, use tool 9.9 instead.

9.2 — rdfs:subPropertyOf: a hierarchy for the verbs new
ekpi:hasTarget a owl:ObjectProperty ;
    rdfs:subPropertyOf ekpi:hasSpecificationElement ;
    rdfs:domain ekpi:KPI ; rdfs:range ekpi:Target .

The same idea as subClassOf, one level up: "whenever hasTarget holds between two things, the broader hasSpecificationElement also holds between them." A query or reasoner asking for a KPI's hasSpecificationElement values automatically picks up its formula, aggregation rule, unit, target, threshold, time period, and grain — without the query author knowing or listing seven narrow predicate names (and without that list going stale when an eighth is added). Three such parents exist: hasSpecificationElement, hasGovernanceRecord, hasSemanticComponent.

9.3 — owl:disjointWith: the impossibility rule

"Nothing can be a member of both classes." The medallion layers are declared pairwise disjoint, so if a load script ever types a dataset as both Raw and Gold, a reasoner flags the graph as logically inconsistent — the data-entry error is caught by mathematics, not by a human reviewer noticing. Disjointness is reserved for genuinely mutually exclusive pairs — and note it needs a real shared parent (Dataset) for "siblings" to even be meaningful, one reason that superclass survived the bucket purge.

9.4 — owl:FunctionalProperty: at most one value
ekpi:hasCertificationStatus a owl:ObjectProperty, owl:FunctionalProperty ;
    rdfs:subPropertyOf ekpi:hasGovernanceRecord ;
    rdfs:range ekpi:CertificationStatus .

ekpi:hasObservationStatus a owl:ObjectProperty, owl:FunctionalProperty ;
    rdfs:domain ekpi:KPIObservation ;
    rdfs:range  ekpi:ObservationStatus .

Declaring a property functional means any subject can have at most one value for it. Two uses now: a definition has exactly one current trust state ("you cannot be simultaneously Draft and Certified"), and — new — an observation has exactly one performance status ("a reading cannot be both OnTarget and Breach"). Both enforced by the ontology, not by application code. (Notice a subject can carry two types after a, comma-separated — it's both an ObjectProperty and a FunctionalProperty.)

9.5 — owl:Restriction + owl:someValuesFrom: "must have at least one" — six times over
ekpi:KPI rdfs:subClassOf [
    a owl:Restriction ;
    owl:onProperty ekpi:ownedBy ;
    owl:someValuesFrom ekpi:BusinessOwner
] .

ekpi:GoldLayerDataset rdfs:subClassOf [
    a owl:Restriction ;
    owl:onProperty ekpi:feedsSemanticModel ;
    owl:someValuesFrom ekpi:SemanticModel
] .

Decode from inside out: the blank node is an anonymous class — "all things that have at least one ownedBy value of type BusinessOwner." Saying KPI is a subclass of that anonymous class means every KPI must satisfy it. RDFS alone cannot express "must have at least one"; this is precisely what justifies OWL's existence.

The six restrictions in plain English: no KPI without a documented definition (the post-migration orphan-KPI gap); no KPI without an accountable owner (the formal KPI-vs-Metric line — a Metric has no such requirement); Raw must trace to a source field (what makes it "raw" rather than "unlabeled"); Silver must trace to Raw (medallion order enforced); Gold must feed a semantic model (what makes it "gold" — consumption-ready — rather than merely "cleansed"). Competency questions 6 and 7 (Part 12) exist to verify these return zero violations.

9.6 — owl:equivalentClass + owl:hasValue: certification as inference
ekpi:CertifiedDefinition owl:equivalentClass [
    a owl:Class ;
    owl:intersectionOf (
        ekpi:KPIDefinition
        [ a owl:Restriction ;
          owl:onProperty ekpi:hasCertificationStatus ;
          owl:hasValue data:Status_Certified ]
    )
] .

The most elegant trick in the file. owl:equivalentClass — the class on the left means exactly the same as the description on the right; membership flows both ways. owl:intersectionOf ( … ) — an RDF list of two conditions that must both hold. owl:hasValue data:Status_Certified — the status property must equal exactly this individual.

Net effect: nobody ever tags anything as a CertifiedDefinition by hand. A reasoner looks at data:RackPriceCaptureRateDefinition_v1, sees its status is Certified, and infers its membership. Change the status to Deprecated tomorrow and the membership silently, correctly disappears. Trust state and class membership can never drift apart — a governance sync problem dissolved by logic rather than process.

9.7 — owl:oneOf: closed enumerations — now five of them
ekpi:ObservationStatus a owl:Class ;
    owl:oneOf ( data:ObsStatus_OnTarget data:ObsStatus_Watch data:ObsStatus_Breach ) .

ekpi:Criticality a owl:Class ;
    owl:oneOf ( data:Criticality_High data:Criticality_Medium data:Criticality_Low ) .

Each class is closed over exactly its listed individuals — nothing else can ever be an ObservationStatus or a Criticality. This is how you model a governed value set (an enum) inside the ontology, so validation and governance dashboards get the allowed states from the model itself. v1 had one such vocabulary; v2 has five — because the review found criticality, thresholdSeverity, and aggregationType living as free strings, the exact "High vs high vs Critical" inconsistency Part 7 lesson 7 warns about.

9.8 — owl:inverseOf: one edge, both directions
ekpi:isFedBy owl:inverseOf ekpi:feedsSemanticModel .

Declares that the two properties are the same relationship read in opposite directions: assert GoldDataset feedsSemanticModel Model, and Model isFedBy GoldDataset is inferred. Queries and navigation work naturally from either end without duplicating assertions (and without the duplicates ever falling out of sync).

9.9 — dcterms:isPartOf + skos:Collection: honest grouping new
ekpi:LineageModule a skos:Collection ;
    rdfs:label "Lineage & Data Architecture Module"@en .

ekpi:GoldLayerDataset a owl:Class ;
    rdfs:subClassOf ekpi:Dataset ;                  # a KIND claim — genuine
    dcterms:isPartOf ekpi:LineageModule ;           # a FILING claim — metadata
    rdfs:label "Gold Layer Dataset"@en .

Not an OWL construct at all — and that's the point. When classes share a topic rather than an essence, the right tool is a metadata edge to a collection individual, not a subclass edge to an invented superclass. This one pattern replaced four bucket superclasses, and the GoldLayerDataset excerpt shows both mechanisms coexisting on one class, each doing its own honest job. "Everything in the Lineage module" remains a one-line query — matched on isPartOf, asserting nothing false. This is the structural signature of v2.0.0.

Part 10

Worked example: tracing Rack Price Capture Rate % end to end

Here is the whole point of the exercise. The §7 individuals form one continuous story from physical columns in two different source systems to a dashboard on a commercial manager's screen — and, new in v2.0.0, all the way to dated observations of how the KPI actually performed. Every arrow below is a literal triple asserted in the file.

The business setup in one paragraph: within the Downstream Commercial domain, the Pricing & Margin Management function owns the Rack Price Management & Publication capability. Its core process, Rack Price Setting, runs four steps: ingest the OPIS rack benchmark → apply zone/freight differentials → publish the rack price sheet → reconcile realized vs. published price. The KPI — Rack Price Capture Rate % = (Realized Rack Revenue per Gallon ÷ Published OPIS Rack Benchmark per Gallon) × 100, per terminal, per product, per day — is a direct proxy for margin leakage at the rack. It aligns to the objective "Improve Rack Price Capture Rate to 99% by Q4 FY26," which narrows the goal "Protect and Grow Commercial Margin."

Forward: how the number is built — two chains feeding one KPI

Backward: the audit question

Start at data:CommercialPricingDashboard and walk the same edges in reverse — dashboard ← semantic measure ← KPI; semantic model ← both gold datasets ← silver ← raw ← source fields ← RightAngle and OPIS. That traversal answers "where does this number on my screen physically come from?" — and its converse answers impact analysis: if NET_PRICE_PER_GAL changes format, which dashboards break? In today's world that answer lives in tribal knowledge; in the graph it's a SPARQL query.

New in v2.0.0: what the KPI actually read — the observation layer

data:RackCaptureObs_Beaumont1_RBOB_20260731 a ekpi:KPIObservation ;
    rdfs:label "Rack Price Capture Rate — Beaumont Rack Terminal 1 / RBOB Gasoline — 2026-07-31"@en ;
    ekpi:measuresKPI data:RackPriceCaptureRateKPI ;
    ekpi:hasObservedValue "96.2"^^xsd:decimal ;
    ekpi:hasUnitOfMeasure data:PercentUnit ;
    ekpi:observedForPeriod data:Day_20260731 ;
    ekpi:observedForDimensionValue data:BeaumontRackTerminal1, data:RBOBGasolineProduct ;
    ekpi:computedAgainstTarget data:Target_99pct_Q4FY26 ;
    ekpi:computedAgainstThreshold data:RedThreshold_97pct ;
    ekpi:hasObservationStatus data:ObsStatus_Breach .

Read it with the Part 5 recipe: this individual is a KPIObservation (an event/fact, not a definition); it points at which KPI it reads; carries the actual number (96.2); says when (a real TimePeriod individual for 2026-07-31) and for which specific dimension values — note the comma: one line, two triples, terminal and product; records what it was judged against; and, because hasObservationStatus is functional, carries exactly one verdict — Breach, since 96.2% sits below the 97% red threshold.

Three observations ship in the file, deliberately spanning states and dimensions: Houston 3 / ULSD on 2026-06-30 at 99.6% (OnTarget), the same terminal/product on 2026-07-31 at 98.4% (Watch — between the 99% target and the 97% threshold), and the Beaumont breach above. The graph represents unhealthy performance as readily as healthy — and a single query can now run from "this specific number, at this terminal, on this day, was in breach" all the way back through measuresKPI and the lineage chains to the exact source field. v1.0.0 structurally could not answer that question at all.

The governance orbit around the KPI

Why the semantic measure sits in the middle — not off to the side data:RackPriceCaptureSemanticMeasure literally sits on the lineage path between the gold datasets and the KPI. If the semantic layer were left as BI-tool config or a spreadsheet, it would be an opaque translation step — invisible to lineage, ungovernable, unqueryable. Modeled as a first-class node, it gets the same trust machinery as everything else, and it solves the reuse problem: define the measure once, consume it from four different surfaces — the ontology's answer to "fifty slightly different revenue definitions."

Part 12

Competency questions — how you know the model actually works

A competency question is a natural-language question the ontology must be able to answer via a graph query once populated — phrased the way a real user would ask it. They are a design input, not a post-hoc QA step: write them before modeling where possible, trace each one end-to-end through the actual classes and properties, and re-run the trace after every revision. Any question you can't trace is a real modeling gap, not a hypothetical one — this exercise is precisely what would have caught the missing Observation layer months earlier, had it been done first (Part 7, lesson 8).

The fifteen questions used to validate v2.0.0, doubling as a starting SPARQL test suite:

#QuestionWhat it exercises
1Which KPIs support the "Rack Price Management & Publication" capability?supportsCapability
2What is the certified definition and formula for Rack Price Capture Rate %, and who approved it?hasDefinition → hasFormula; hasVersion → approvedBy → ApprovalEvent
3Which source systems and fields ultimately feed a given KPI's Gold dataset?derivedFromMeasure → derivedFromDataset → prov:wasDerivedFrom chain → originatesIn
4If NET_PRICE_PER_GAL in RightAngle changes format, which dashboards or scorecards are at risk?The Part 10 backward walk, run forward from a SourceField
5Who is the current data steward for a given KPI, and since when?stewardedBy (shortcut) + hasStewardshipAssignment → assignmentStartDate (record)
6Which KPIs have no BusinessOwner asserted?The ownership restriction — should return zero violations
7Which Gold datasets do not yet feed any SemanticModel?The medallion restriction — should return zero violations
8What was the observed value for Houston Terminal 3 / ULSD on a given day, and was it on target?The observation layer: measuresKPI, observedForPeriod, observedForDimensionValue, hasObservationStatus
9Which terminal/product combinations breached their threshold in the last period?hasObservationStatus = Breach, grouped by DimensionValue
10Which business terms have alternate labels ("synonyms"), and what are they?skos:altLabel on BusinessTerm — the deleted Synonym class's job, done properly
11Which consumption assets would be affected if a specific SemanticMeasure were deprecated?consumedBy fan-out across all four consumption types
12What is the full chain of custody — source field to dashboard — for a KPI value shown to an executive?The complete Part 10 trace, both lineage chains
13Which KPIs are measured against the same underlying Measure (candidates for consolidation)?derivedFromMeasure joined across KPIs — the anti-duplication query
14Which policies, standards, and controls govern a given KPI?governedByPolicy → implementsStandard → enforcedByControl
15Which strategic objectives currently have no KPI tracking them?A coverage-gap query — deliberately not yet enforced by a restriction; a candidate for future tightening

Notice questions 6 and 7 are special: they exist to verify the restrictions — in a healthy graph they return nothing, and anything they do return is a governance violation the model itself detected. And notice question 15's footnote: knowing what you've chosen not to enforce yet is part of honest modeling too.

14.1 — Mini glossary (plain language)
TermPlain-language meaning
TripleOne fact: subject – predicate – object. The atomic unit of RDF.
IRIA globally unique name for a thing — a very precise, permanent address.
NamespaceThe common IRI "stem" shared by a family of related terms.
PrefixA short nickname for a namespace, so you don't type full IRIs.
ClassA category of things (KPI, Dataset, KPIObservation).
IndividualOne specific instance of a class (this KPI; this reading of it on 2026-07-31).
Object propertyA relationship between two things.
Datatype propertyA relationship between a thing and a plain value (string, number, date).
LiteralA plain value like "96.2" or "2026-07-31", optionally typed with ^^xsd:…
Blank nodeAn unnamed helper node, written [ … ], for facts that need no address of their own.
Domain / RangeA property's function signature: what may sit on its left and right.
rdfs:subClassOf"Every member of the first class is also a member of the second." A real logical claim about kinds — never a convenience label.
rdfs:subPropertyOfThe same idea one level up: every use of the narrow property implies the broader one also holds.
dcterms:isPartOf + skos:CollectionHonest grouping without a taxonomy claim — files a class under a module without asserting shared kind-hood.
RestrictionA formal constraint on how a property may be used for members of a class.
owl:oneOfCloses a class to an exact, fixed list of individuals — a governed enumeration.
owl:FunctionalPropertyA property that can hold at most one value per subject.
ReasonerSoftware that checks consistency and derives new facts (like inferred class membership) from asserted ones.
SPARQLThe query language for RDF graphs — SQL's cousin for triples and paths.
OntologyA formal, machine-readable specification of a domain's concepts and relationships.
Competency questionA user-phrased question the ontology must answer via a traceable query — a design input and regression test.
Bucket superclassThe anti-pattern: a superclass invented purely to group topic-mates. Fails the genuine-kind test; use a module tag instead.
Orphan classA class declared but never instantiated or connected — silent debt to remove, implement, or explicitly defer.
Fact / observation layerThe part of an ontology recording what actually happened (dated, dimensioned readings), as opposed to how things are defined.
LineageThe traceable path showing where data came from and how it was transformed.
Medallion architectureThe Raw/Bronze → Silver → Gold refinement pattern of modern data platforms.
Semantic layerA governed translation layer mapping physical data to business meaning.
CertificationA governance state confirming an asset is trusted and approved.
Rack price / rack captureThe posted terminal ("rack") price fuel is sold at; capture rate measures how much of the published benchmark a terminal actually realizes — a margin-leakage proxy.
